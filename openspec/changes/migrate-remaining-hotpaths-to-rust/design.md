## Goals / Non-Goals

**Goals:** Remove redundant traversal, serialization copies, and ownership graphs at existing component seams. Use one implementation of shared ownership rules wherever possible. A component's implementation size is not a proxy for its benefit.

**Non-goals:** Replace PyMongo BSON scalar codecs or transport; redesign selective invalidation; change public APIs, eligibility, consistency, platform support, wire format, or owner-selection protocol. Existing requirements in `cache-core`, `cached-read-api`, `change-stream-coherency`, and `shared-worker-cache` remain authoritative. Existing evaluation requirements still apply; this change's deltas add the staged-development and owner-accounting obligations.

## Decisions

### D1. Integrated stages with one final release comparison

Use the assessment-table order and independent commits, keeping each retained stage as the next stage's control. The candidate always runs through ordinary constructors; there is no experimental backend switch to integrate later. Baseline installations supply the preceding implementation. The final comparison uses a frozen current-main release wheel, not PR #355's older Python wheel.

A single branch has a practical advantage: capture, key preparation and owner admission share encoded payloads and keys, and all use the same extension. Separate PRs would repeat wheel builds and broad confirmation without removing those dependencies. There is no known need to split now. Stop to discuss a split only if implementation requires a separate public/wire/platform change, or the owner transition cannot be reviewed without an independent protocol redesign. Show the concrete dependency or diff before deciding; module count alone does not establish that problem.

Alternatives: an all-at-once rewrite hides attribution and makes rollback difficult; separate PRs isolate reviews but multiply acquisition and integration costs; a research-only fork cannot deliver the requested result. None requires further research. Stage costs and final interaction effects are answered by tasks 1.1–1.3 and 6.1.

### D2. Encoded capture, retaining driver codecs

The data path becomes:

```text
PyMongo yields document
  -> existing codec-aware embedded-document encoding
  -> native accumulator appends immutable bytes with BSON array framing
  -> natural exhaustion produces one encoded value envelope
  -> existing guarded admit_namespace_encoded operation
```

Accumulate into one growable buffer; do not build Python `RawBSONDocument` wrappers or a Python snapshot list. Reserve conservatively and use checked BSON length arithmetic. Appending remains linear in encoded bytes overall, with geometric buffer growth. Finish patches lengths and transfers or copies the completed contiguous envelope once; it does not decode/re-encode documents. Preserve non-leading `_id` order by retaining embedded-document encoding rather than substituting top-level `bson.encode(document)`.

The current append bound counts document bytes; final admission additionally counts array element names and the envelope. Preserve both decisions, including rejection counters and timing, so an exact-bound candidate is not silently rejected earlier. Empty results, encoder failure, abandonment, cancellation, stale generations, and manager close retain their current behavior. Destruction releases native buffers even while a closed cursor remains reachable. Started hits continue to own independent snapshots.

Alternative: a Python byte builder can remove wrappers with less native code, but still executes per-item framing in Python; use it only as a diagnostic if native boundary overhead prevents a gain. A new Rust BSON serializer could remove codec calls but would duplicate application codec semantics and maintenance. That is disproportionate and needs no prototype. Native call overhead and actual transient memory remain unknown until tasks 2.1–2.2.

### D3. Fused preparation without narrowing supported values

Use one Rust traversal to validate supported shapes and produce the existing canonical key tree, avoiding Python pending-tree construction followed by another canonical traversal. Keep Python wrappers where callers require them; move shared pure logic behind those wrappers rather than maintaining divergent rule tables. The portable shared-find encoder remains the wire authority. Reuse prepared results only for immutable execution snapshots; mutable caller inputs must still determine the next execution's key.

Preserve scalar-find permutation rules, ordered embedded documents, identity numeric equivalence, discriminator `int`/`Int64`/float distinctions, boolean tags, codec identity, custom mappings/sequences, supported opaque leaves, and exception/bypass precedence. Unsupported native fast shapes use equivalent generic handling, not a newly introduced bypass. User callbacks, comparisons, hashing, conversion, and decref-triggered destructors run outside native locks; existing version revalidation still governs cache effects.

Alternative: a compact opaque native key could save more allocations, but would change comparison and cross-path key integration simultaneously. First preserving the representation limits compatibility risk while still removing repeated traversals. Reimplementing every helper independently in Rust retains redundant work and is rejected without further research. Whether the chosen representation saves complete-operation CPU is unknown until tasks 3.1–3.2; a different representation needs a revised design decision if this candidate does not qualify.

### D4. Shared owner reuses native state and owns publication atomically

Extract reusable internal state operations from `native/shared-index/src/local_cache.rs` without changing the ordinary local-owner interface. Add an internal shared-owner binding using those operations and the existing `OwnerIndex` arena/index primitives. Resident values distinguish owned bytes from arena handles; the owner keeps exactly one resident payload, and publication stores a reference to it. Arena allocation failure preserves the current owner-served byte fallback. Socket-only mode must remain functional.

Move `IndexPublisher`'s resident publication/token/identity/find maps into the native shared owner, so eviction and invalidation do not require mirrored Python entry graphs. Replace `_drain_rings`' private `_lru.touch` access and `_admit_local`'s `_availability_lock` access with complete native operations. Metadata probing and capture release need explicit equivalent methods instead of emulated Python locks. Python keeps authentication, sockets/selectors, PyMongo stream supervision, and handle/session transport policy initially; repeated frame dispatch can join the native owner only when attribution supports it.

Preserve the existing progress/availability/capture order: validation, current generation checks, payload residency, and publication must form one guarded transition. Keep the ordering progress gate -> native core state -> index writer, with no reverse acquisition or Python callback under either native lock. Touch tokens need generation validation so recycled tokens cannot touch replacement entries. Retire payloads and Python references outside critical sections after publication has been withdrawn. Preserve incarnation, epoch, local capture age, namespace-slot reuse, queue bounds, and fallback semantics.

Alternative: adding generic Python observer/payload callbacks to `LocalCacheCore` is a smaller bridge, but retains Python publication maps and extra crossings in the operation being optimized. Maintaining an independent Rust shared LRU/identity implementation duplicates the already-correct local algorithms. Moving networking and stream supervision too would add an unrelated runtime/lifecycle migration. The reusable-state approach has the clearest default; exact owner CPU distribution and allocation lifetime are unresolved measurements in tasks 4.1–4.4, not reasons to postpone successful integration.

### D5. Remaining routing and dispatch decisions use current attribution

Profile ordinary real-server reads and event processing after retained stages. If a remaining Python responsibility contributes removable repeated work, integrate its pure routing/classification into the native operation and use the same decision process. Do not infer that a small fraction is automatically worthless: the question is whether repeated complete-operation measurements establish a benefit. A component with no identified removable work receives a concrete no-change rationale in the report.

For stream routing, preserve all write/create/drop/rename/index/history-loss behavior, metadata-cache notifications, and clock-skewed lag semantics. Python supervision remains responsible for retries and resumption. Native routing is compared using real events processed by the manager, not calls to a routing helper.

Alternative: porting every Python wrapper would maximize Rust line count but add driver-binding obligations with no established resource gain. Retaining every remaining helper without assessing it could leave avoidable overhead. Tasks 5.1–5.2 resolve the measurement unknown; no broader rewrite or follow-up research task is assumed.

### D6. One short benchmark per candidate, one combined full run

This section owns workload selection. Task 1.1 records exact commands and source/build identities in `reports/native-internals/plan.md` before candidate timing, referencing this section rather than duplicating it. Use the existing collectors and acquisition harness. Preserve the historical #355 configuration when adding a current-run configuration; its fixed test-node hash and frozen source identities cannot be used unchanged for this revision.

The current registration must also replace `acquire.py`'s `native = arguments.label == "F"` assumption and `contention.py`'s resulting Python-core expectation for M. M and F identify revisions, not implementation types: both current-main and candidate contention cells use their installed native `LocalCacheCore`. Derive expected implementation provenance from the registration and assert actual core type, installed package paths, and wheel/extension hashes against each build's recorded identity. Preserve the historical Python-versus-native expectations only for the historical registration; do not merely remove installation assertions.

**Development preflight.** Follow the five-minute bound in the delta spec. Use a disposable replica set, one repetition, 16 keys, 32 reads per worker and 16 documents of 128 bytes, both API models and affected local/shared paths. Verify cold admission and a subsequent hit for the same shape before shutdown. Include an aggregate/large-result spot check when capture changes, and owner-queue draining when shared processing changes. Keep relevant focused correctness cases outside benchmark timing. Run this preflight after runtime edits and before committing time to longer acquisition.

For D4, include an additional shared `identity` cold-admission-to-hit check in this same five-minute preflight. Start with ready metadata and absent identity results, enable native admission queues and collector diagnostics (`--diagnostics`), and verify a positive delta in worker `native_admissions`, completed owner processing reconciled with those submissions, zero pending admissions, and subsequent expected hits without origin reads. Require the diagnostic counters to be present: the current collector returns no endpoint counters without diagnostics. A find-only run or successful socket fallback does not demonstrate the queued `admit-local` path. The deadline covers all preflight cells together, including teardown, rather than granting each cell five minutes.

An existing starting command is:

```bash
source scripts/testcontainers-bridge.sh
timeout --signal=TERM --kill-after=15s 300s <installed-python> -m benchmarks.public_shared_cache --method find --hot-keys 16 --samples 32 --result-documents 16 --document-bytes 128 --models sync async --paths independent shared --workloads cold hot --repetitions 1 --validate --output /tmp/agents/native-internals/STEP-smoke.json
```

The collector must own teardown on interruption; the outer timeout is a last-resort failure bound, not its cleanup mechanism. Build/install time is recorded separately. Current collector gaps are aggregate validation, worker/budget/entry-limit parameters, same-shape cold-to-hit checks, and admission-drain accounting. Extend those existing paths only as needed by the selected cells.

Preparation also requires an explicit workload variant in `benchmarks/public_shared_cache.py`; its current `find_one` filter is only `{"group": identity}` with a sort. For the registered target, use `{"group": identity, "ordinal": {"$in": list(range(256))}}`, descending ordinal sort, and one result document per group. This preserves 1,024 distinct generic query keys and returns that group's ordinal-zero document. Use the same query construction and per-read allocation policy in both builds and API models; warm and measure the identical full predicate. Validate predicate length/content, expected values, exact hit counts and zero measured origin reads, and record the selected variant in provenance so the simple-filter workload cannot silently substitute for it.

**One candidate benchmark.** Each integrated candidate gets one preregistered acquisition lasting less than 30 minutes total, including both builds, all internal repetitions, profiling and teardown. Compare it with its retained predecessor using three counterbalanced paired repetitions of the target and one adjacent regression control in both API models. Use preflight/baseline-only duration to fix sample counts before candidate timing; the sample counts below are starting ceilings, not a requirement to overrun the budget. If even the reduced acquisition cannot complete, record the invalid or inconclusive outcome and resolve that concrete problem instead of starting a full campaign.

| Candidate                                                | Target cell                                                                                                          | Adjacent regression control                                                                                                   |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Capture                                                  | Complete cold 4,000 × 1,024-byte `find`, at most 32 reads per worker; 8 MiB entry limit and a fixed admitting budget | Warm small-result `find`; aggregate, partial/oversized and custom-codec behavior is exercised by preflight/correctness cases. |
| Preparation                                              | Complete hot generic `find_one` with a 256-element `$in`, 1,024 resident keys, at most 4,096 reads per worker        | Small hot identity reads, including the existing portable-key path.                                                           |

Use the production topology for the changed operation; capture/preparation default to independent managers and owner work to shared managers. Required safety and alternate-path correctness cases remain separate from performance sampling. Broad local/shared, memory, eviction and contention performance coverage belongs to the existing combined full run rather than every candidate acquisition.

Include bounded baseline/candidate attribution samples in that same short acquisition, separately from uninstrumented timing. Profile at most 256 complete reads per worker or 256 processed real events. Capture owner profiles in the owner process; worker profiles and owner busy-wall counters do not establish owner CPU attribution. Record repeated traversals/copies/callbacks and component cost in the assessment map. Later candidates use the current retained tree as their baseline, so work already removed is not claimed twice.

Retain exact results, cache outcomes, origin commands, CPU per complete operation, P50/P95/P99, throughput and process/group memory observations for the selected cells. Resource accounting for shared work includes all admissions through completed owner processing: submitted counts must reconcile with outcomes, pending records must be zero, and residency must stabilize. Report foreground latency separately from drain time, while keeping the drain's CPU in the resource interval. MongoDB and harness resource use remain separate. Register an equal-residency memory target before candidate timing if memory is the proposed qualifying benefit; transient observations alone cannot substitute for it.

The short benchmark provides component attribution and early regression detection. Apply the existing stable-benefit and adverse-trade-off rules without inventing a minimum percentage or treating nested requests as independent runs. Report paired directions/ranges and noise; an unclear result remains inconclusive. There is no automatic uncertainty cohort or extra confirmation campaign. Correct a concrete failure or investigate a specific adverse signal with narrowly affected checks, retaining the earlier result; additional runs need that stated reason.

**One existing combined campaign.** After all three main candidates and any justified folded-in work settle, run the pre-existing multi-hour benchmark once as a matched frozen-main versus combined ordinary-wheel campaign. Reuse `research/native_local_integration/acquire.py` and its existing public/memory/contention orchestration with a current registration and refreshed existing-test selection. Keep its normal coverage rather than adding a second full matrix. Add a missing candidate-specific cell only when the short benchmark and existing campaign otherwise leave that operation unmeasured; include it within this same run.

The combined report uses the component short-run evidence alongside that final campaign; an aggregate gain cannot conceal a known losing component. Existing real-process correctness/fault gates still apply to owner changes, without launching the unfinished historical full-protocol research study. Repeat a failed or invalid affected portion only when a correction or unresolved regression requires it. Final evidence that remains inconclusive is reported as such, with the existing implementation retained for an unqualified component. No whole multi-hour rerun follows a documentation-only edit.

Alternatives: full per-component campaigns multiply cost before integration errors are found; isolated helper microbenchmarks omit codecs, queues, wheel loading and origin work. The selected schedule follows the user's development-time budget while retaining a final broad regression check. Collector suitability and actual runtime are resolved in tasks 1.1–1.3; no additional benchmark framework or routine uncertainty campaign is needed.

## Risks / Trade-offs

- Native buffers can reduce traced Python memory while increasing total retention -> measure process peaks, warm/close checkpoints and repeated cycles; do not use `tracemalloc` alone to qualify.
- Shared-owner changes cross publication and reclamation boundaries -> operation-ordering/race cases compare owner truth with worker-visible values, including failed arena allocation and reused namespace slots.
- Strong opaque Python references can create cycles or trigger reentrancy on release -> retain native GC traversal/clear support and retire objects outside locks.
- Combining stages can mask a losing component -> apply the per-component delta requirement before the final aggregate comparison.
- Long runs can consume container resources -> retain existing topology cleanup, abort visibly on setup failures, and avoid changing host limits or deleting unrelated resources.

## Migration Plan

The existing extension and packaging remain the delivery mechanism, including supported Linux x86-64/ARM64 wheels. A component's commit can be reverted independently to its predecessor. Remove Python code only once no supported production or exported API path uses it; the public `CacheCore` contract and socket-only shared mode preclude assuming that all `_core/manager.py` code becomes dead. Preserve rejected measured source as required by the existing evaluation spec. Public documentation changes are needed only for user-visible effects; internal Rust mechanics belong here and in commit bodies.
