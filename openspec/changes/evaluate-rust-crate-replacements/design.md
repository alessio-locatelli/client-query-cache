# Design

## Context

Source inspection at `b983e75f` confirms the hash, decimal conversion, slot allocator, and dual-map probe tracker described in the supplied assessment. `rustc-hash` already serves selected integer collections behind the `python` feature. Other native maps still use standard hashers. `scoped_hash` mixes Python hashes before a second map hashes the result. This is an investigation lead, not proof that the two stages are redundant: they serve different indexing roles.

`Sizer::pending` is reused within one sizer and reserves `KEY_NODES`; `Pins` and `MetaPins` already specialize empty/one/many cases. The assessed `echo.rs` socket implementation is absent. The maintained native workload runner imports production PGO workloads and supports selecting names. Release settings and measurement caveats are documented in `docs/development/native-quality.md`.

## Goals / Non-Goals

See `proposal.md` for scope and the delta spec for acceptance. This is an internal substitution effort, not a replacement cache engine. Python dependencies, allocator changes, generic concurrent-cache migrations, and numeric-vector libraries are outside scope. Neither process-local collections nor thread queues replace the memory-mapped index, arena, or interprocess queues.

## Decisions

`bytes` has no current socket target and is excluded. The alternatives above cover the meaningful local choices; wholesale replacement of specialized caches or memory-mapped structures is disproportionate and needs no prototype in this change.

### D2. Preserve behavioral and compatibility boundaries

The existing `cache-core`, `cached-read-api`, `change-stream-coherency`, `selective-invalidation`, `shared-worker-cache`, and `production-library-scope` specs remain the behavioral authority. Candidate-specific verification is identified in D1.

Keep collision-resistant strategies for user-controlled names and Python-derived hash buckets unless a concrete equivalent safety argument establishes otherwise. Never equate hashes with key equality. Retain callbacks outside critical sections and revalidation after callbacks.

For a shared-hash replacement, encode the namespace and each byte field with explicit fixed-width lengths/domain boundaries and fixed byte order; avoid concatenation allocations and per-process random state. Use a documented deterministic algorithm/seed shared by owner and readers. A changed hash mapping changes index compatibility even when word offsets are unchanged: increment the existing index layout version and verify incompatible attachment is rejected. Do not introduce dual-hash fallback or persisted-index migration. Crate updates that change hash output must repeat that compatibility decision. A randomized shared seed would improve some attack resistance but adds shared protocol state and is outside this focused substitution; if needed for safety, reject this candidate and surface that decision.

Do not mechanically replace poisoned locks. If preserving current behavior needs a custom poisoning layer or a user-visible panic-policy change, reject `parking_lot` for that lock and record why. Such a policy change would require a separate user decision; no unresolved policy choice is delegated to implementation.

### D3. Time-efficient comparative method

Apply the delta's `Staged acquisition avoids repeated full campaigns` rule to screening, confirmation, A/A checks and final combined-build controls. Start each registration by answering: "What is the smallest duration we need to distinguish between noise and the net effect?" Use existing comparable variance estimates where available; otherwise justify a minimal pilot to estimate batching cost, variation and plausible effect. Include warmup, subprocess setup, repetitions, controls and teardown in the planned elapsed acquisition time; report compilation separately. Correctness suites are separate from acquisition.

Before timing, record baseline/current-main and candidate source identities, hypothesis, data shapes, target metric, duration rationale, planned repetitions, stopping criteria and operational timeout. These acquisition identities do not establish durable reproduction; use D4 for retained references. Use pilot evidence to choose a fixed confirmation sample independently of its observations, or a prespecified sequential method that accounts for repeated looks; repeatedly checking an ordinary confidence interval is not a valid stopping method. A timeout yields an explicit incomplete result. Compare a single candidate with its predecessor; use frozen current main again for the final combination. Use identical workload source, compiler, release configuration, dependency versions except the candidate, telemetry policy, interpreter, and host conditions. Verify imported binary paths/digests. Default-disabled telemetry stays disabled; use result assertions and command monitoring for cache outcomes, with enabled telemetry measured only where affected.

Use counterbalanced A/B repetitions and an identical-build A/A control, batching enough work to amortize clocks and consuming outputs to prevent optimization away. Choose repetition counts from the duration rationale rather than a universal count. Screening intervals are exploratory. Implement the delta's performance-qualification rule by registering the comparison family before screening, including independently selectable sites, alternatives and qualifying metrics. Use a Bonferroni allocation of the family's 5% error budget across those comparisons, with confirmation intervals at the allocated confidence levels. Freeze that family and allocation before screening; later unregistered alternatives remain exploratory and cannot qualify a performance claim in this campaign. This uses the established [single-step correction](https://www.statsmodels.org/stable/generated/statsmodels.stats.multitest.multipletests.html), not an additional runtime dependency.

Confirm performance-based winners on fresh observations with a confirmation workload/sample fixed after screening and before acquiring confirmation data. Independently rebuild both baseline and candidate for confirmation; for release-wheel claims, repeat profile training too, yielding at least two builds per source across screening and confirmation. Compare same-source rebuilds separately from identical-binary A/A to estimate build variation. Preserve build-level grouping when calculating uncertainty: repeated timings of one binary are not independent builds. Qualify only if the confirmation's adjusted uncertainty resolves a positive effect beyond timing and build variation; otherwise collect further evidence only under the duration rule or leave performance inconclusive. Maintenance-based decisions use their separate qualification route and cannot borrow a screening speedup claim. A simple snippet remains sufficient for isolated operation claims. Integrated controls do not promote those claims to complete cached-read gains.

Reuse `research.native_build_profile.compare`, `measure`, and `end_to_end` where their workload selection and verified production interfaces fit. Useful existing names include `wire_keys`, `capture_array`, `shared_hit_small`, `shared_publish_cycle`, `admit_churn_small`, and `write_invalidation`. A compile-time-only Rust microbenchmark can exercise private functions when no production binding exists. Add no runtime inspection API or selectable production backend, and retain no duplicate baseline implementation. Small development harness changes are preferable to a new benchmark framework. Raw output and throwaway experiments belong under `/tmp/agents/`.

Measure elapsed time per completed operation plus allocation/retention for storage changes and contention behavior for lock changes. Integrated controls select the affected hit, admission and invalidation paths, with both local/shared and sync/async where the changed operation is used. The final installed release builds receive a small combined control set, including extension size and startup/import memory; storage candidates also compare equal-residency churn memory. Full P95/P99 and every historical workload are not an automatic per-crate requirement. The CI guard's material-slowdown threshold is not an acceptance/noise threshold here; investigate every reproducible adverse result as required by the existing regression policy.

For the delta's contention rule, trace each candidate's protected work before selecting controls. `Probes::begin` and `finish` run under the owner state mutex, so candidate 3a needs concurrent probe refresh/completion alongside competing reads or admissions on that same owner. Match offered load and record throughput and tail/wait latency to expose longer critical sections. This focused control does not require the full cache-core invalidation campaign. Other candidates document why their protected-work cost can or cannot materially affect contention.

Alternative: repeat the historical full native-migration campaign for each crate. It offers broader coverage but repeats resolved questions and can spend time refining precision without changing a decision. Alternative: impose the same short cap on every candidate. It bounds cost but can reject an informative longer run or overmeasure an easy decision. Alternative: one stopwatch run is cheaper but cannot distinguish a small gain from noise. The chosen method spends time according to expected decision value; task 1.1 prepares its stopping controls.

### D4. Qualification and durable evidence

The delta's `Proven gains qualify regardless of percentage` owns the two qualification routes. For maintenance decisions, report which custom algorithm or coordinated state disappears and what adaptation/invariants remain; fewer lines alone are not evidence of simpler ownership. Performance uncertainty cannot be hidden behind maintenance value. Resolve failed controls and report inconclusive ones; use the staged-acquisition rule to decide whether more measurement would help.

Apply the delta's reporting and source-reproducibility requirements using AGENTS.md's artifact-value policy. Record candidate dispositions and supporting/adverse observations in the PR description when they serve review alone. Create `reports/rust-crate-replacements/summary.md` or retained workloads only for lasting engineering value; keep disposable experiments and raw samples local. No dedicated branch, tag or source copy is created solely to preserve a rejected experiment.

For an experiment worth reproducing, record build configuration, workload, exact dependency/features, source-content digests and reconstruction commands against stable integrated source. Identify accepted source through the integrated PR result or a release reference, not a pre-merge SHA. Rejected changes need a reproducible transformation from that source, rather than instructions to fetch an abandoned commit; verify the transformation in a fresh checkout using only the retained material before cleanup. If sufficient reconstruction detail would have no maintenance or review value, discard the experiment without promising reproduction. Do not retain obsolete runtime implementations. Update public guides or Context7 only when public usage instructions change; put useful internal guidance in the retained evidence or native development guide.

## Risks / Trade-offs

- Small isolated effects may disappear across Python calls or PGO builds → bound claims to measured scope and retain D3 controls and limitations.
- A dependency can move complexity into adapters or retained allocations → use the D1 compatibility screen and D4 maintenance accounting before adoption.
- Multiple independent improvements can interact → compare the final ordinary build with frozen main under D3, investigating adverse signals before acceptance.

## Migration Plan

Ship accepted substitutions through the ordinary native build with no runtime switch. For the shared-hash candidate use D2's version rejection and recreate owner/worker mappings on restart. Roll back by reverting the relevant substitution commit and rebuilding/restarting the group; never attach mismatched hashes to an existing mapping.

## Open Questions

Measured benefits, suitable inline capacity, and net adapter complexity remain unknown until the D1 tasks. They determine candidate disposition, not the workflow or public contract. No crate has been benchmarked or approved for adoption during planning.
