## Context

The composed recovery seam, cache core, and change-stream manager provide the prerequisites for user-visible cached reads. The API is deliberately narrower than transparent interception of all PyMongo methods.

## Goals / Non-Goals

**Goals:** Provide equivalent sync/async reads, `_id`-based identity caching, safe generic result caching, and raw escape hatches.

**Non-Goals:** This change does not cache writes, change sessions, or admit partially consumed cursor data. It does not cache declared-unique-key reads either: `_id` is the only identity this change treats as an alias-free document identity; unique-key discovery and alias-based identity caching are substantial enough to warrant their own change and are deferred to a follow-up once this facade foundation lands.

## Decisions

- Wrap supplied PyMongo collections; expose raw collections for unsupported operations.
- Detect whether the wrapped collection is backed by a MongoDB view (its data depends on the namespace(s) named in the view's `viewOn`/pipeline, not the view's own namespace) and mark it cache-ineligible if so: bypass cache lookup and admission for every read against it, since writes to its backing namespace(s) never advance the view's own namespace generation and change-stream events for those writes are routed under the backing namespace, not the view's. This is the same conservative treatment as cross-collection aggregation stages below, applied at the collection level instead of per-pipeline. A namespace can become a view either by an existing collection being dropped and recreated, or by coming into existence as a view for the first time; both advance the namespace epoch (`implement-cache-core` advances the epoch on `create` as well as on clear, precisely so a namespace's first appearance is not silently missed). The facade therefore does not check collection type on every read, only the first time it handles a read for a namespace after observing that the namespace epoch has advanced past the one recorded at its last check — this re-verification is rare (only after a drop/rename/clear/create) rather than a per-read cost, and it covers both a wrapper created for an ordinary collection that is later recreated as a view, and a wrapper created before its namespace existed at all. This guarantee is scoped the same way as every other invalidation in this system: it holds once the manager's change-stream worker has processed the `create`/clear event that made the namespace view-backed, not at the instant the DDL runs on the server. A read that races ahead of that event delivery may still observe the prior eligibility determination — this is the same bounded/eventual coherency `implement-change-stream-coherency` already documents for ordinary writes, not a new, weaker promise invented for views.
- Treat `_id` as the only document identity this change caches by. An `_id` read always knows its document identity before issuing the database read, so it captures that identity's identity generation and the namespace epoch up front and admits an identity-guarded entry, keyed by that identity and the read's shape (per `implement-cache-core`) — it does not capture or depend on the namespace generation, so writes to other documents in the same namespace never invalidate it. An `_id` read is always safe to query the database by `_id` directly, because the caller explicitly asked for that identity; whatever that document currently looks like is the correct answer regardless of what else about it may have changed. A cache miss simply queries `find_one({"_id": ...})` with the caller's original projection unchanged — there is no alias to resolve or re-verify, since the query already names the identity directly.
- Cache other fully materialized results (an equality read on any field other than `_id`, plus `find`/aggregate/count/estimated-count/distinct) as namespace-guarded entries behind cache-core's per-collection namespace generation, so writes anywhere in that collection conservatively invalidate membership and ordering. Treating a non-`_id` equality read as a generic namespace-guarded result rather than as an identity alias is deliberate for this change: aliasing a field the caller merely asserts is unique (without verifying it against the database's own index metadata) is a distinct, sizable piece of work — deferred to a follow-up change once this facade foundation is in place — and until then such a read is simply a bounded generic result like any other filtered `find`.
- Force eligible cache-admitted reads to primary plus majority. If the caller selected a secondary or non-majority read profile on the wrapped collection or operation, bypass both cache lookup and admission and preserve the caller's PyMongo read options.
- Admit `find`/aggregate only after complete materialization and capacity validation. Sync and asyncio share behavioral tests but use native driver APIs.
- Reject aggregation pipelines containing a cross-collection stage (`$lookup`, `$unionWith`, `$graphLookup`), a write stage (`$out`, `$merge`), a live-statistics stage (`$collStats`, `$indexStats`, `$planCacheStats`), a `$sample` stage, an expression that executes caller-supplied JavaScript (`$function`, `$accumulator`), or a nondeterministic or time-dependent expression at any nesting depth (`$rand`, `$sampleRate`, and the system variables `$$NOW` and `$$CLUSTER_TIME`) from caching, and reject a `$changeStream` pipeline outright rather than execute it: admit only pipelines whose result depends solely on reading the wrapped collection and is deterministic given the collection's current contents, guarded by that collection's namespace generation as with any other derived result. A `$lookup`/`$unionWith`/`$graphLookup` pipeline reads a foreign collection that cache-core's per-namespace generation guard has no way to depend on without tracking every namespace a pipeline touches and validating all of them atomically at admission — added complexity this change defers until hit-rate data justifies it. A `$out`/`$merge` pipeline has a database write side effect on every execution; caching its result would skip that side effect on a later hit, which silently breaks the pipeline's own semantics regardless of invalidation correctness. A `$collStats`/`$indexStats`/`$planCacheStats` stage reports live collection, index, or query-plan counters that change as the server executes operations against that collection — including reads, which never advance the namespace generation — so a cached result would freeze those counters indefinitely with nothing to invalidate it against; this is a distinct hazard from the cross-collection and write cases above, since the stage reads only the wrapped collection's own namespace, but the value it reports is not a function of that namespace's document contents the generation guard tracks. A `$changeStream` pipeline is rejected outright rather than merely excluded from caching: `aggregate` always fully materializes its result via `to_list()`/`list()`, and a change-stream cursor is designed to never end on its own, so treating it the same as the other bypassed-but-executed pipelines here would hang the caller indefinitely instead of returning an uncached result — the same reasoning that already excludes tailable/exhaust cursor types from `find()`, applied to the one aggregation stage that produces the same kind of cursor. A `$sample` stage, a `$rand`/`$sampleRate` expression, or `$$NOW`/`$$CLUSTER_TIME` can each produce a different result on every execution with no write to the collection at all — `$sampleRate` is `$rand`-shaped nondeterminism with a different distribution, always embedded via `$expr` (e.g. `{"$match": {"$expr": {"$sampleRate": 0.33}}}`) rather than usable as a bare filter key, matching MongoDB's own documented syntax; `$$NOW`/`$$CLUSTER_TIME` are fixed for the duration of one pipeline run but vary across runs, the same caching hazard as `$rand` through a different mechanism; caching any of them would freeze a nondeterministic or time-dependent query to its first answer indefinitely, which the namespace-generation guard has no way to detect since nothing invalidates it. `$function`/`$accumulator` are rejected unconditionally rather than inspected: they execute an opaque, caller-supplied JavaScript body that could reference `Math.random()`, the current time, or any other nondeterministic or side-effecting construct with no structural marker to detect — unlike `$rand`/`$sampleRate`/`$$NOW`, which are named operators a static scan can find, JavaScript source text can hide the same hazard in a way no reasonable static check can rule out, so rejecting on presence is the only sound option. This list of nondeterministic constructs is not exhaustively enumerable from MongoDB's own documentation; it covers the well-known cases and is expected to grow if others are identified. Bypassing these pipelines (same treatment as partial/tailable/oversize reads) is the conservative default: it never returns stale joined data, skips a write side effect, or freezes a random or time-dependent result, at the cost of caching nothing for these pipeline shapes for now. The same hazard reaches `find`, `count_documents`, and `distinct` through their plain filter document, not only through aggregation pipelines: a filter containing `$where` embeds arbitrary JavaScript, the same unconditional-rejection reasoning as `$function`/`$accumulator` applies, and a filter containing `$expr` embeds the same aggregation-expression syntax a pipeline can, including `$rand`/`$sampleRate`/`$$NOW`/`$$CLUSTER_TIME` and `$function`/`$accumulator` themselves — `$expr` is a general query operator, not aggregation-only, so `find({"$expr": {"$sampleRate": 0.33}})` and `find({"$expr": {"$function": {...}}})` are both valid syntax outside a pipeline too. Reject a `find`/`count_documents`/`distinct` read whose filter contains `$where`, or an `$expr` containing one of the same nondeterministic, time-dependent, or opaque-JavaScript expressions rejected in pipelines, from caching, for the identical reasons.
- Wrap `count_documents`/`estimated_document_count`/`distinct` results in a single-field BSON envelope document before admission, so cache-core's existing BSON storage, weight measurement, and encode/decode isolation apply unchanged to non-document values.
- Admit `find`/aggregate results only after complete materialization and BSON-encoding for this change (see Resource and Complexity Costs): an oversized result pays the full materialization and encoding cost before being discarded. This is the deliberately simple option; the alternative — tracking encoded size incrementally as documents arrive and abandoning cache admission once the running total exceeds the budget, while still streaming the full result to the caller — is real but adds meaningful complexity to cache-core's admission contract (currently "encode once, atomically, at a point tied to the pre-read generation capture") for a benefit that only matters for read-heavy workloads with large results. Whether to build it is deferred to `benchmark-change-stream-costs`, which includes a dedicated oversized-result workload (exceeding the max-entry size) to measure exactly this cost; see that change's `tasks.md` for the tracked follow-up task rather than leaving the question open here indefinitely.

## Likely Bottlenecks

Materializing a `find`/aggregate cursor and BSON-encoding it to measure size against the cache-core budget means the CPU, memory, and allocation cost of a large result is paid in full even when the result turns out to be too large to cache and is discarded — no check avoids encoding the data at all, since the budget is defined in encoded BSON bytes. What full materialization does forgo is failing fast: encoding and checking size incrementally as the cursor streams, rather than only after every batch has arrived, could abandon an over-budget result without paying for the untouched remainder. Whether that is worth the added admission-contract complexity for this change is deferred to benchmark evidence (see Decisions). For read-heavy workloads with large or unbounded result sets, full materialization's cost is expected to dominate over the cache-core storage operations themselves. `count_documents` and `estimated_document_count` avoid this because they return a small, near-constant-size command result. `distinct` does not: an unindexed filter over mostly-unique values can produce a distinct-value list that approaches collection scale, carrying both the server-side scan cost and the client-side encode-before-validate cost of the cursor path.

## Risks / Trade-offs

- [Generic result invalidation is broad] → Namespace-generation invalidation favors correctness over hit rate.
- [Materialization uses local memory] → Apply cache-core entry limits and never admit partial or oversize results.
- [A cached aggregation result has no way to depend on a foreign namespace] → Bypass caching entirely for pipelines containing `$lookup`, `$unionWith`, or `$graphLookup` rather than risk returning stale joined data.
- [A cached `$out`/`$merge` result would skip that pipeline's write side effect on a hit] → Bypass caching entirely for pipelines containing `$out` or `$merge`.
- [A view's data depends on a namespace the cache doesn't track] → Detect views and bypass caching for every read against them, rather than risk stale results from writes to the backing collection.
- [A collection wrapped while ordinary could later be dropped and recreated as a view] → Re-verify collection type whenever the namespace epoch has advanced since the last check, rather than trusting a one-time determination made at wrap time forever.
- [View eligibility can only be revoked once the change-stream worker processes the event, not at the instant the DDL runs] → Scope the guarantee to "after event processing," matching the bounded/eventual coherency already documented for ordinary writes, rather than claiming an instantaneous guarantee the architecture can't deliver.
- [A canonical-identity-only key could let a projected `_id` read collide with a full-document read for the same document] → Key identity-guarded entries by (identity, read shape), matching cache-core's contract, rather than by identity alone.
- [A cached aggregation result could depend on the wall-clock time it was computed at, via `$$NOW`/`$$CLUSTER_TIME`, with no write to invalidate it] → Bypass caching for pipelines using these system variables, the same conservative treatment as `$rand`/`$sample`.
- [`$sampleRate` (always `$expr`-embedded, per MongoDB's own documented syntax — never a bare filter key or stage) was missing from the nondeterministic-expression list, in both pipelines and plain filters] → Add it alongside `$rand`; the existing `$expr`-scanning mechanism already catches it in both contexts once it's in the list.
- [`$where`/`$expr` in a plain `find`/`count_documents`/`distinct` filter can be just as nondeterministic as an aggregation pipeline, but only pipelines were scanned] → Reject filters containing `$where`, or `$expr` embedding the same nondeterministic expressions already rejected in pipelines.
- [`$function`/`$accumulator` let a pipeline execute opaque, caller-supplied JavaScript that no static scan can prove deterministic] → Reject them unconditionally on presence, the same treatment as `$where`, rather than attempt to analyze the JavaScript body.
- [Full materialization pays the complete cost of pulling and encoding an oversized `find`/aggregate result before rejecting it, but incremental size tracking would add real complexity to cache-core's admission contract] → Ship full materialization for this change; defer the incremental alternative to a benchmark-gated decision tracked in `benchmark-change-stream-costs`.
- [Caching only `_id`-keyed identity reads for this change leaves every other equality read (e.g. a lookup by a unique `email` field) on the lower-hit-rate generic namespace-guarded path] → Accepted for this change; unique-key discovery and alias-based identity caching is deferred to a follow-up change rather than folded into an already-large facade foundation.
- [A wrapped collection configured with non-default `CodecOptions` (e.g. a non-default UUID representation or timezone-aware datetimes) would have its already-decoded values re-encoded and later re-decoded by cache-core using BSON's default codec, which can raise on ambiguous UUID encodings or silently change a value's representation on a cache hit] → Thread the wrapped collection's own `codec_options` through every admission and lookup call, so cache-core's encode/decode round-trip uses the same codec the query itself used. This does not address two collection handles for the same namespace sharing one `CacheManager` with genuinely different `codec_options`; that residual collision is not defended against, since resolving it requires a hashable codec fingerprint cache-core does not have a use for otherwise.
- [A collection wrapped with non-default `CodecOptions` (e.g. a non-default UUID representation, or timezone-aware datetimes) captures an `_id` identity value decoded under that codec, but the change stream that invalidates it decodes `documentKey._id` with the database's own (typically default/unspecified) codec; for any codec-dependent BSON type these two decodes can disagree — a `uuid.UUID` under a legacy representation decodes to a different `Binary` subtype, and a timezone-aware `datetime` decodes as naive — so cache-core's identity comparison would treat them as two different identities, and `record_write` silently misses the cached one, leaving a stale identity-guarded entry after an external update or delete] → Normalize any `_id` identity by round-tripping it through BSON under the read codec's `CodecOptions` and back out under the change stream's `CodecOptions` (`normalize_identity_for_cache_key`), rather than special-casing UUIDs alone: this reproduces whatever representation change the stream's own decode would apply to the same underlying document, covers every codec-dependent type uniformly without enumerating them, and falls back to the original identity unchanged if the value cannot be encoded at all.
- [Some BSON values (e.g. `bson.Code`, a `str` subclass that overrides `__eq__` without defining `__hash__`, making instances unhashable) cannot be hashed, but cache-core's `canonicalize()` needs to hash arbitrary nested values to build a cache key. The same hazard reaches `is_filter_cacheable`/`is_pipeline_cacheable` even earlier: `_contains_unsafe_construct`'s scan for nondeterministic system-variable strings (`$$NOW`, `$$CLUSTER_TIME`) checked `node in unsafe_variables` against every string-typed node, including such an unhashable `str` subclass, and raised `TypeError` from that membership test before caching was ever considered — turning an uncacheable read into a hard failure instead of a graceful bypass] → Guard the `unsafe_variables` membership check in `_contains_unsafe_construct` against `TypeError` (an unhashable string-like value cannot be one of the named system variables, so treat it as not matching), and separately check `is_canonicalizable()` — whether cache-core's `canonicalize()` can hash a value without raising — before ever handing an identity or discriminator to cache-core, in `find_one`/`find`/`aggregate`/`count_documents`/`distinct`; when either check fails, bypass caching and execute the read directly, the same conservative treatment as an oversized or nondeterministic result.
- [Cache-core's `canonicalize()` treats `Mapping` values as order-insensitive by deliberate, tested design (`implement-cache-core`'s `test_canonicalize_treats_as_equivalent` asserts `{"a": 1, "b": 2}` and `{"b": 2, "a": 1}` canonicalize identically) — but MongoDB's own exact-equality semantics for an embedded-document filter value, and its own multi-field `$sort` priority, are both BSON-field-order-sensitive, so `find({"x": {"a": 1, "b": 2}})` and `find({"x": {"b": 2, "a": 1}})`, or `{"$sort": {"x": 1, "y": 1}}` and `{"$sort": {"y": 1, "x": 1}}`, are different reads that canonicalize's default handling would treat as one cache key, letting the second silently reuse the first's cached result] → For namespace-guarded discriminators (`find`, `aggregate`, `count_documents`, `distinct`), recursively convert every `Mapping` in the discriminator into an order-preserving tuple of `(key, value)` pairs (`order_sensitive_key`) before it reaches `canonicalize()`, so nothing Mapping-shaped is left for canonicalize's own order-insensitive handling to collapse. This is safe to do unilaterally here, unlike the identity case below, because a namespace-guarded entry's invalidation is a blanket generation bump on any write, not a match against a specific canonicalized identity — reducing incidental collisions on this path can only improve correctness, never break write invalidation.
- [The same order-insensitive `canonicalize()` behavior also affects a compound (embedded-document) `_id` used as an identity, where MongoDB's own exact-equality semantics are equally BSON-field-order-sensitive, so two distinct documents whose compound `_id` has the same fields in a different order would collide under one identity-guarded cache entry] → Left unfixed for this change, unlike the discriminator case above: forcing order-sensitive comparison for identities alone, without a matching change to how the change-stream event router (`implement-change-stream-coherency`, already archived) canonicalizes `documentKey._id` for `record_write`, would trade this rare collision hazard for a write-invalidation-miss hazard instead, which is worse — identity-guarded invalidation depends on matching the same canonical identity `record_write` computes, unlike the namespace-guarded case. A correct fix needs coordinated changes to both capabilities and is deferred; callers with compound `_id` schemas should use a consistent field order to avoid the collision in the meantime.
- [A wrapped collection's codec can successfully decode a value PyMongo returns (e.g. via a custom, read-only `TypeCodec`) that cache-core's own `encode_value` cannot re-encode for storage, which would otherwise raise `bson.errors.BSONError` out of `admit_identity`/`admit_namespace` and fail a read that would have succeeded without caching at all] → Catch `BSONError` around the encode step in both admission methods and return a new `DECLINED_UNENCODABLE` outcome instead of propagating; admission is always optional, so a value cache-core cannot store is treated the same as one that is merely too large, and the facade — which already ignores the admission outcome — returns the already-fetched value unaffected.
- [`$collStats`/`$indexStats` report live counters unrelated to a collection's document contents, a hazard distinct from the cross-collection, write, and randomness/time cases already rejected] → Add both, plus `$planCacheStats` (the same live-statistics hazard for query-plan counters), to the pipeline rejection list, the same conservative bypass-and-execute treatment as the others.
- [`$function`/`$accumulator` were rejected unconditionally for aggregation pipelines but not for an `$expr`-embedded plain filter, even though `$expr` carries the full aggregation-expression language into `find`/`count_documents`/`distinct` the same way it does for `$rand`/`$sampleRate`/`$$NOW`/`$$CLUSTER_TIME`] → Reject `$function`/`$accumulator` in filters too, closing the same gap already closed for the nondeterministic-expression list.
- [A `$changeStream` aggregation pipeline produces a cursor with no natural end; treating it merely as "bypass caching but still execute" like other rejected pipelines would hang the caller on `to_list()`/`list()` indefinitely, since this facade always fully materializes an aggregation's result] → Reject `$changeStream` pipelines outright with a clear error before attempting execution, the same category of fix already applied to `find()`'s tailable/exhaust/partial-result cursor types.
- [`ensure_cache_eligible` returned eligible purely from view status, ignoring whether the database's change stream was currently healthy; during recovery this forced primary/majority read options onto a read that could never be cached anyway, which could block or fail a read that the caller's own, weaker read profile would have satisfied] → Check database availability first and bypass immediately when unavailable, before ever consulting or forcing read options, so a read during recovery keeps exactly the behavior it would have without the cache layer at all.
- [A failed view-inspection probe (`list_collections` raising `OperationFailure`, e.g. an unauthorized caller) was treated as `is_view=True` and memoized in `CollectionMetadataCache` the same as a genuine view determination; because that cache is only re-checked after the namespace epoch advances, a transient or later-resolved probe failure disabled caching for that collection indefinitely — not just for the read that hit the failure, but for every subsequent read, with no way to recover short of an unrelated drop/recreate/clear on that namespace] → Have the probe report three outcomes instead of two (`True`/`False`/unknown, via `bool | None`) and never memoize the unknown outcome: `ensure_cache_eligible` bypasses the current read without writing a `CollectionMetadata` entry when the probe returns `None`, so the very next read re-probes from scratch rather than trusting a stale failure. This repeats the probe on every read for as long as the failure persists — the same repeated-attempt trade-off already accepted for the change-stream startup-failure fix above — but self-heals as soon as the underlying condition clears, instead of requiring an unrelated namespace event to force a recheck.
- [`ensure_cache_eligible` called `activate_database` unconditionally; against a standalone server, a server predating the minimum supported version, or one that otherwise rejects `show_expanded_events`, `activate_database` raises `StreamStartupError` before this method can ever return `False`, so every otherwise-supported read against that database failed outright instead of falling back to the caller's raw PyMongo collection — the same server conditions `change-stream-coherency` already documents as "fail closed" for stream startup, but surfaced here as a hard failure of the read itself rather than a bypass] → Catch `StreamStartupError` where the coordinator starts a database's stream and return without propagating it, leaving the database's cache-availability flag at the `False` value the supervisor already set before attempting to start; a subsequent read then takes the existing unavailable-database bypass path unchanged. This does not change the underlying retry behavior: because a failed startup attempt is not stored as an active supervisor (mirroring the existing successful-activation-is-memoized-but-failure-is-not behavior), a database whose server can never satisfy the startup check pays another `server_info` round trip and stream-open attempt on every subsequent read that reaches `ensure_cache_eligible`, rather than being remembered as permanently unavailable; that repeated-attempt cost already existed before this fix (it previously ended in a crash instead of a bypass) and is accepted as-is here, since deciding whether a startup failure is permanent (unsupported server version) or transient (a connection blip) and giving each its own retry policy is a distinct, larger design question than closing this crash.
- [`is_canonicalizable`/`canonicalize` treated any hashable value as a safe cache key, but a BSON `NaN` (a `float` that fails `hash()` never, yet is never equal to itself, `nan != nan`) hashes without error and so passed this check; a dict/set keyed by one `NaN` value can never be found again by a _different_ `NaN` instance with the same bit pattern, since dict/set lookup falls back to `==` (which is always `False` for NaN) once identity (`is`) fails to match. An `_id` read using a `NaN` identity would therefore admit an identity-guarded entry that `record_write`'s own freshly change-stream-decoded `NaN` object could never look up to invalidate, leaving that entry servable indefinitely after an external update or delete] → Reject any value that is not equal to itself (the standard `value != value` test for NaN-like values) in `canonicalize`, the same terminal check as the existing unhashable-value rejection; this folds into the identity-admission and `record_write` bypass paths already built for unhashable values, so a `NaN` identity is now treated as uncacheable rather than admitted under a key nothing can ever match again.
- [Cache-core's `canonicalize()` already tags a `bool` separately from an `int` because Python's numeric tower makes `True == 1` and `hash(True) == hash(1)`; the same numeric-tower equality holds between `int` and `float` (`1 == 1.0` and `hash(1) == hash(1.0)`), but only `bool` was tagged. A generic-result discriminator built from an aggregation pipeline containing, for example, `{"$literal": 1}` versus `{"$literal": 1.0}` — two pipelines that are different and produce differently BSON-typed results — canonicalized to the same key, so the second pipeline's `aggregate` call could hit the first's cached (wrong-numeric-type) result] → Tag a `float` the same way `bool` already is, wrapping it in a dedicated tag before it can collide with a plain `int` at the same value; the fix intentionally does not extend to other numeric-tower members (e.g. `Decimal`) or to `bson.Int64` (a subclass of `int` that decoding never actually produces — BSON int32/int64 both decode to plain `int`), since neither is a reachable collision from PyMongo's own decode behavior.
- [`pipeline_blocks_full_materialization`'s recursive scan for a `$changeStream` stage did not distinguish a pipeline stage position from a value nested anywhere else in the pipeline document tree, so a pipeline such as `{"$project": {"value": {"$literal": {"$changeStream": 1}}}}` — where `$changeStream` appears only as inert literal data guarded by `$literal`, never as an actual stage — was rejected outright as if it opened an unbounded change-stream cursor, when it is in fact an ordinary, fully materializable pipeline] → Check only the pipeline's own top-level stage objects for the `$changeStream` key, rather than recursing into each stage's expression body: `$changeStream` is only ever valid as a pipeline stage itself (the first element of the pipeline array), never as an aggregation-expression operator usable inside `$project`, `$literal`, or similar, so a non-recursive per-stage check is both sufficient and precise. This narrower check applies only to the change-stream-blocking scan; `is_pipeline_cacheable`/`is_filter_cacheable`'s recursive scan for the other unsafe/nondeterministic keys is unchanged, since a false positive there only forgoes a caching opportunity rather than rejecting an otherwise-valid read outright.
- [Cache-core's `record_write` canonicalized the write's document identity before advancing the namespace generation; when that identity could not be canonicalized (the same unhashable-BSON-value hazard `is_canonicalizable` already guards reads against), the call raised out of the stream worker's event-processing loop instead of returning. Neither sync nor async worker wraps that loop in a catch-all, so the raise was fatal to the worker thread/task, which then exits silently: the namespace generation for every document in that database's namespaces stops advancing from that point on, so previously admitted namespace-guarded entries keep being served as cache hits indefinitely, even though writes keep happening on the underlying collection] → Advance the namespace generation unconditionally, before attempting to canonicalize the identity, and skip only the identity-specific generation bump when the identity cannot be canonicalized; a document whose identity cannot be canonicalized was never itself admitted as an identity-guarded entry (the same `is_canonicalizable` check declines admission for it in the facades), so skipping the identity-specific step loses no correctness, while advancing the namespace generation unconditionally preserves the existing "a write invalidates namespace-guarded entries for the whole namespace regardless of which document it touched" contract cache-core already documents.

## Migration Plan

Implement sync identity reads first, add bounded generic reads, then establish asyncio parity and ownership/error tests against independent raw writers.
