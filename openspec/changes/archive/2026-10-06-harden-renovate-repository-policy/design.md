# Design

## Context and scope

Renovate owns unsupported executable pins through custom regex, Actions tool inputs, nodenv, and pyenv; Dependabot owns supported manifests and action references. Keep that split and the existing coupled MongoDB, Prek, and Taplo replacements. [The delta spec](specs/dependency-update-automation/spec.md) is the source for numeric budgets, cadence, release ageing, and acceptance obligations.

## Decisions

### Preset composition

Extend `config:best-practices` and `:semanticCommits` before the existing custom-manager presets. The [best-practices baseline](https://docs.renovatebot.com/presets-config/#configbest-practices) supplies maintained grouping, integrity, pinning, abandonment reporting, and security-age policies within existing ownership. This avoids maintaining a copied list of its constituent policies.

Exclude `:maintainLockFilesWeekly` and `:configMigration` through `ignorePresets`. Lockfiles belong to Dependabot; [configuration migration](https://docs.renovatebot.com/configuration-options/#configmigration) is experimental and creates configuration PRs outside dependency-update scope. Remove local `lockFileMaintenance` and `automerge: false` settings. Renovate's disabled automerge default is intentional: the shared App workflow owns acceptance for both bots, with no `:automergeAll` preset or duplicate merge request.

Also exclude [:ignoreModulesAndTests](https://docs.renovatebot.com/presets-default/#ignoremodulesandtests) using [nested preset exclusion](https://docs.renovatebot.com/configuration-options/#ignorepresets). Its global test-directory ignore would hide `tests/conftest.py` before the MongoDB custom manager extracts it, leaving only `benchmarks/stream_cost/topology.py`. Retain the existing enabled managers and scoped file patterns to control ownership; inherit the default module-directory ignores without a local `ignorePaths` copy.

Remove MongoDB's `allowedVersions` field and the Python/Node version-cap rules. Use Renovate's [native nodenv manager](https://docs.renovatebot.com/modules/manager/nodenv/) to maintain one `.node-version` file. `actions/setup-node` reads it with `node-version-file`; the container derives `nodejs${NODE_MAJOR}` and `nodejs${NODE_MAJOR}-npm` package names from it. Hash the file in tooling cache keys and classify changes as requiring both formatting and container checks. RPM versions still resolve from Fedora rather than a bot-managed RPM pin. If Fedora lacks a proposed Node major, the required container build fails and prevents acceptance; no static major cap or separately edited specification is needed. Inherit [Docker versioning](https://docs.renovatebot.com/modules/versioning/docker/) for suffix and precision handling. Add only the necessary MongoDB `pinDigests: false` override, scoped to `custom.regex` and Docker: its replacement is tag-only ([upstream limitation](https://github.com/renovatebot/renovate/issues/24942)). Keep Taplo checksum replacement and the preset's pyenv exemption. Implement the spec's budgets using `prConcurrentLimit`, `prHourlyLimit`, and `commitHourlyLimit`; inherit branch concurrency. Express its monthly window with cron and an explicit UTC timezone.

### Development Python and compatibility coverage

Renovate's native pyenv manager owns `.python-version` and may advance to stable Python releases; the package's `requires-python` lower bound remains a compatibility declaration. The workflow calls `scripts.ci_python_matrix`, keeping matrix selection directly testable without parsing workflow shell text. Generate packaging and full-test matrices containing the exact lower bound, intermediate supported release lines, and the exact `.python-version`. Deduplicate only identical interpreter requests; a development patch update on the minimum release line still retains both exact versions. The existing composite action exposes setup-uv's `python-version` override, which sets `UV_PYTHON`; isolated release validation honors it too. Matrix cache keys and failure artifact names include the lane.

A stable `Python compatibility` job aggregates both matrices and fails on any unsuccessful applicable lane. Require this aggregate rather than release-specific matrix check names, so a Python update cannot require manual ruleset registration for its new lane. The container smoke check resolves its selected interpreter with `uv python find`, without a versioned executable name. Python hooks deliberately retain the lowest supported release line, independent of development Python; [Prek installs requested interpreters](https://prek.j178.dev/reference/language-support/#python) when needed. Updating the package compatibility floor is a separate deliberate change. The performance guard already uses the head-selected interpreter for both revision environments, preserving like-for-like measurements during a Python update.

### Required CI without current-base enforcement

Use GitHub [loose required checks](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging): require existing checks, but leave “Require branches to be up to date before merging” unchecked. Require the stable checks in `.github/workflows/test.yml`, including scope selection, quality prerequisites, and the Python compatibility matrix aggregate; resolve displayed check names and the GitHub Actions source from successful runs during operator activation. Keep path-selected skips, contributor approval, stale-review dismissal, linear history, and the permitted rebase merge method; grant no bypass.

Strict checks would offer stronger integration assurance, but [Dependabot rebasing](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#rebase-strategy) is conflict- or schedule-driven and cannot guarantee prompt updates after a non-conflicting base push. A branch-update controller adds privileged automation; a merge queue adds validation triggers and platform prerequisites. Loose checks satisfy unattended acceptance with fewer builds, accepting that later base changes may interact with a previously green PR. Omit `rebaseWhen` and inherit Renovate's behavior. No additional controller or queue research is required for this choice.

### Shared App acceptance

Run `dependency-automerge.yml` from main on a successful `workflow_run` completion of the existing `Pull request validation` workflow for both bots. [Dependabot's `pull_request_target` restriction](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-on-actions) prevents that event from accessing secrets; [the completion workflow can access them](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#workflow_run), even when validation could not. Keep `workflow_dispatch` with a PR-number input for one-time activation of existing PRs: require ref main and rely on [GitHub's write-access requirement for dispatch](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) to authorize the operator.

Use live API metadata only; never check out PR code, install from it, consume run artifacts, or write caches. Require the triggering run to be a successful `pull_request` run of `.github/workflows/test.yml` with a same-repository head and an original bot actor (Dependabot or Renovate). A human push to a bot-authored PR must not qualify. A human rerun of a bot-initiated run retains that original actor and validated SHA; it may qualify, while dispatch remains the explicit operator path for other existing PRs. Resolve associated PRs through GitHub's commit-to-PR API, since the run's `pull_requests` array can be empty. Select exactly one open, non-draft Dependabot/Renovate PR whose head repository matches this repository, base is main, and live head equals the triggering run's head SHA. Dispatch selects the live PR/head directly. A read-only selection job supplies the PR number and SHA to an acceptance job serialized by PR for both paths. Revalidate before requesting credentials, approve the verified commit, then revalidate again before `gh pr merge --auto --rebase --match-head-commit "$HEAD_SHA"`. A stale completion must not approve a later revision. GitHub required checks remain the final merge gate; do not poll CI or merge unconditionally.

Use SHA-pinned `actions/create-github-app-token` with repository variable `DEPENDENCY_AUTOMERGE_APP_ID` and secret `DEPENDENCY_AUTOMERGE_APP_PRIVATE_KEY`. Scope installation tokens to this repository with Contents/Pull requests write and no bypass. Keep built-in workflow permissions read-only. Without App configuration, report inactive acceptance visibly and perform no approval or merge request.

An App adds one-time setup but preserves post-merge workflows: [GITHUB_TOKEN event suppression](https://docs.github.com/en/actions/concepts/security/github_token) can prevent documentation publication after a bot merge. A PAT adds a personal credential; removing contributor approval weakens the existing review policy. One App path also avoids Renovate's [fallback to direct automerge](https://docs.renovatebot.com/configuration-options/#platformautomerge) before platform activation. Token, review, merge-method, and trigger behavior require operator verification after deployment; task 2.1 prepares those checks.

## Deployment boundary

The coding agent prepares and validates repository files only. Task 2.1 writes a post-merge operator checklist in the contributor guide with this order:

1. Discover and snapshot current effective main rules and repository settings; configure loose required checks without altering unrelated rules or granting bypass.
2. Provision/reuse the scoped App, confirm its installation and permissions, then supply its ID and private-key secret without exposing the key.
3. Enable repository auto-merge and verify both bots' approvals, native rebase merging, failing-check enforcement, behind-base acceptance, and applicable post-merge publication. Dispatch trusted management on main for pre-existing bot PRs as a one-time activation step, using `gh workflow run dependency-automerge.yml --ref main -f pr_number=<number>`.
4. Inspect hosted discovery read-only. File presence and local dry runs establish neither hosted success nor a no-PR cause. Record inaccessible evidence as unverified; persistent discrepancies need a tracking-ticket URL.

Record live operations and their rollback separately from the code PR. Disabling repository auto-merge alone is insufficient for already-enabled PRs: cancel their pending automerge requests, withdraw App credentials/access, and restore operator-owned settings from the snapshot as appropriate. Code rollback is a normal revert. Missing administrative access or credentials blocks activation, not completion of the reviewed repository PR.
