## Context

See proposal.md - Why. Today `AGENTS.md` lists setup and quality commands as a flat sequence across five separate CLIs (`uv`, `prek`, `ruff`/`mypy`/`taplo` invoked directly, `npm`), none of them declared as an installable dependency of the project itself. This change is sequenced in the roadmap after `bootstrap-test-environment`, so by the time its test/coverage recipes are implemented, that change's unit/integration/end-to-end/benchmark pytest markers and its Testcontainers-owned replica-set fixture already exist - this design wraps them rather than inventing placeholder test-tier behavior ahead of the change that owns it. `bootstrap-test-environment`'s own design.md is silent on running its Docker/Podman-backed fixture from inside a rootless-Podman container (toolbx/Distrobox) on an immutable host, which is how this project's own development happens today; that gap is what this change's container-runtime-access decisions close.

## Goals / Non-Goals

**Goals:**

- One command surface (`just <recipe>`) for setup and every quality/test command.
- A buildable container image that gives a contributor the full toolchain without a hand-rolled install script.
- A documented, safe way for a contributor working inside that container to reach a container runtime for Testcontainers-backed tests.

**Non-Goals:**

- Does not change what the quality workflow checks or what the test tiers do - only how contributors invoke them and where they run. `bootstrap-test-environment` still owns test-tier semantics.
- Does not publish or host the container image; contributors build it locally.
- Does not support Docker Desktop or non-Linux hosts; scope is Podman-based toolbx/Distrobox on a systemd Linux host, matching this project's actual environment. Distrobox can run on non-systemd hosts in general, but this design's socket-enablement recipe manages `podman.socket` through `systemctl --user`, so a systemd user session is a prerequisite here regardless of container type.

## Decisions

- **The Containerfile owns toolchain acquisition; `setup` owns project-level environment setup, and assumes the former already happened.** `prek` is a standalone binary today, per `AGENTS.md`'s own note that it is "not a uv dependency" - `uv sync` cannot install it, so `just setup`'s `prek install` step needs `prek` already on `PATH`. The container image (task 2.1) is what puts it there, alongside `taplo`, `zizmor`, and `just` itself. `setup` is therefore documented and scoped as a recipe that runs inside the provisioned container (or an equivalent host that already has the same toolchain), not as a recipe that bootstraps a bare host from nothing; conflating the two would make `setup`'s "no additional manual command" guarantee false on a host that only has `uv` and `git`.
- **Task runner: `just`.** A `justfile` covers `uv`/`npm`/`prek`/container recipes uniformly without `PHONY` boilerplate or Python-only assumptions. Considered `make` (available everywhere but awkward for non-file-target tasks) and `tox`/`nox` (already used for the Python test matrix, but can't naturally wrap `npm`/`prek`/container recipes) - `just` was already the tool the user asked to standardize on.
- **`lint` keeps today's existing hook behavior; `format` fills the one gap that leaves.** `.pre-commit-config.yaml`'s Ruff-check, Ruff-format, and Taplo hooks already write fixes and fail if anything changed - `just lint` (`uv run --locked --all-groups -- prek run --all-files`) keeps that exact, already-relied-upon behavior rather than trying to force it read-only, which would mean diverging from what commit-time hooks already do for the same checks. It runs through `uv run` rather than a bare `prek run` because the `slotscheck` hook is configured `language: system` and expects `slotscheck` to already be resolvable from `.venv/bin`, which `uv run` puts on `PATH` without requiring a separate manual venv activation. The one command genuinely dropped once `AGENTS.md` stops documenting raw commands is the write-mode `npm run format`: Prek's own local Prettier hook intentionally runs the read-only `npm run format:check` instead (`.pre-commit-config.yaml:82-89`), so nothing else provides the fix. `format` therefore wraps only `npm run format`, not a redundant copy of the Ruff/Taplo fixers `lint` already applies.
- **Every `uv run` in a recipe passes `--locked`.** `uv run` on its own can silently rewrite `uv.lock` to match a `pyproject.toml` that changed without a matching regenerated lock, resolving the mismatch _before_ Prek's `uv-lock --check` hook (or anything else) gets a chance to see it - which would let `just lint` (and `test`, `coverage`, `test-integration`, `test-e2e`) pass instead of reporting the drift the existing `development-environment` "locked project is out of date" requirement demands. `--locked` makes `uv run` fail instead of quietly reconciling the two.
- **`test` stays unit-only; `coverage` is a separate, combined-tier gate.** `test` selects `bootstrap-test-environment`'s `unit` marker explicitly rather than running pytest unfiltered, matching that change's existing contract that the default command runs unit tests without a container runtime, even after integration/e2e tests exist in the same suite. `coverage`, `test-integration`, and `test-e2e` are separate recipes: `bootstrap-test-environment` requires _combined_ production branch coverage across every applicable in-process tier at the configured 81.10 percent regression threshold, so a unit-only coverage run cannot satisfy it - `coverage` therefore also runs the integration tier and needs container-runtime setup in the same recipe body as its pytest invocation, since `just` recipes run in independent subshells and a variable exported by one recipe (e.g. `DOCKER_HOST`) is not visible to a different recipe invoked afterward. The coverage recipe isolates its data in a fresh temporary directory, rejects production `pragma: no cover` markers explicitly, and still runs `strict-no-cover` for its unnecessary-exclusion check.
- **Multi-step runtime-access recipes use a `#!/usr/bin/env bash` shebang, not plain `just` lines.** By default, `just` runs each line of a recipe as its own separate shell invocation - state does not survive from one line to the next even _within_ the same recipe, let alone between two different recipes. The runtime-access recipes (3.1's container-type detection and two-layer probe, 3.3's `DOCKER_HOST` assignment feeding a later pytest invocation, 3.4's coverage gate) all need that state to persist across lines, so each is written as a shebang recipe: the whole body runs as one script under one shell, exactly like a normal Bash script would.
- **One Containerfile, two consumers.** A single `Containerfile` declares the pinned toolchain (Python 3.14 via `uv`, Node.js, npm, `prek`, `taplo`, `zizmor`, `just`) and is consumed as a custom image by either `toolbox create --image` or `distrobox create --image`, instead of maintaining two bootstrap scripts. Toolbx is the documented default because it ships natively on Silverblue and is what this environment already runs; Distrobox is a fully supported alternative for contributors who need its broader host-integration options.
- **The immutable-host bootstrap does not require `just`.** Requiring the task runner before creating the image that provides it adds a circular host dependency and is inconvenient on Fedora Silverblue. The documented one-time bootstrap therefore uses the host's existing `podman build` and `toolbox create` or `distrobox create` commands directly. The matching `just` recipes remain optional conveniences on hosts where `just` is already available; all project setup, quality, and test work uses the pinned copy inside the contributor container.
- **No nested Podman, and container-type-specific socket paths.** Contributors reach the host's rootless Podman rather than running a second Podman daemon inside the toolbx/Distrobox container:
  - toolbx mounts the host's `$XDG_RUNTIME_DIR` into the container at the same path as part of its standard D-Bus/Wayland integration, so once the host's `podman.socket` unit is enabled, it is reachable inside the toolbx at the same `/run/user/$(id -u)/podman/podman.sock` path as on the host ([containers/toolbox host-system-integration docs](https://deepwiki.com/containers/toolbox/2.3-host-system-integration)).
  - Distrobox instead remaps the host's runtime directory under `/run/host` inside the container, so the same socket is reachable at `/run/host/run/user/$(id -u)/podman/podman.sock` ([Distrobox useful-tips docs](https://distrobox.it/useful_tips/)). Treating this the same as toolbx's path would silently fail to connect.
  - The `DOCKER_HOST` recipe therefore branches on container type and uses the path documented above for that type, rather than assuming one universal path.
  - `DOCKER_HOST` itself must be a `unix://`-prefixed URL (e.g. `unix:///run/user/$(id -u)/podman/podman.sock`), not the bare filesystem path - the Docker SDK Testcontainers uses parses it as a URL and a bare path is invalid.
  - On Distrobox, `DOCKER_HOST` alone is not enough for the integration/e2e/coverage recipes: Testcontainers' Ryuk cleanup sidecar asks Podman to bind-mount the socket into a new container, and Podman resolves that bind source on the host, not from the caller's remapped view - so the Distrobox-side `/run/host/...` path that works for the direct API connection does not exist from Podman's own perspective and Ryuk's mount fails. Those recipes also set `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` - a bare filesystem path, not a URL, per Testcontainers' own configuration - to the host-visible path (`/run/user/$(id -u)/podman/podman.sock`, without the `/run/host` prefix) so Testcontainers uses that path specifically for the mount source. toolbx does not need the override, since its path is identical on both sides.
  - Interactive `podman` CLI use, and the one-time host `podman.socket` enablement, go through each container type's host-execution bridge: `flatpak-spawn --host podman ...` for toolbx (the pattern documented upstream for exactly this case: podman-project mailing list, containers/toolbox#1003), and `distrobox-host-exec podman ...` for Distrobox - Distrobox's own equivalent, built on the same `host-spawn` mechanism `flatpak-spawn` implements. Neither container type gets a free pass to assume shared D-Bus alone reaches `systemctl --user`; both route through their bridge explicitly.
  - Installing and running Podman _inside_ the contributor container was rejected: toolbx/Distrobox bind-mount the contributor's home directory, so a nested Podman daemon reads/writes the host's own `~/.config/containers` and can corrupt it (containers/toolbox#1003).
- **One-time host wiring goes through a `just` recipe, not manual docs.** A recipe (e.g. `just enable-podman-socket`) detects which container type it is running in and runs `flatpak-spawn --host systemctl --user enable --now podman.socket` (toolbx) or `distrobox-host-exec systemctl --user enable --now podman.socket` (Distrobox), so it is unambiguous that this configures the host's systemd user instance, not whatever `systemctl --user` would otherwise resolve to from inside the container.
- **Pin the whole toolchain, not just Python.** The Containerfile pins Node.js, `uv`, `prek`, `taplo`, `zizmor`, and `just` to explicit versions, and the base image to an exact digest (`FROM <image>@sha256:...`, not a tag) - a tag is not immutable, since a registry can retarget it to a different image later, which would silently change the base OS and its preinstalled tools out from under an otherwise-identical Containerfile. This matches the existing `uv`/PyMongo pinning discipline. Installing an exact CPython patch release (`uv python install <patch>`) does not by itself make `uv sync`/`uv run` select that interpreter when others are present, so interpreter selection needs a `.python-version` file (via `uv python pin <patch>`) - but that file has to be a tracked file at the repository root, not something baked into the image: toolbx/Distrobox mount the contributor's home directory over the checkout path, which shadows anything the image placed there, so a `.python-version` written during the image build would never be visible to `uv run`/`uv sync` invoked from the actual mounted checkout. The image's job is only to pre-install the pinned patch so it doesn't need a network fetch later; the repository's own `.python-version` is what makes `uv` actually select it. Verification is `uv run python --version`, run from the mounted checkout, reporting the pinned patch, not just the `3.14` minor line.
- **Verify reachability in two layers: the host service's actual state, then the in-container path.** Podman is daemonless, so `podman info` run through the bridge can succeed against local state even when `podman.socket` is disabled or failed - it does not prove the socket-activation unit is up. The first check therefore queries the unit directly through the bridge (`systemctl --user is-active podman.socket`), not `podman info`. That still says nothing about whether the socket is reachable at the path the container sees - a wrong toolbx/Distrobox mount, a missing forward, or an in-container permission problem would all pass a host-only check and still break Testcontainers later - so a second check runs from inside the container and connects to the container-type-specific path directly. That second check does not need a Podman client - a one-line Python connection attempt against the Unix socket (Python is already pinned in the image) is enough to prove something is listening and accepting connections at that exact path, which is the actual failure mode worth catching before Testcontainers hits it.

## Risks / Trade-offs

- [A future toolbx/Distrobox release changes its default runtime-directory mount path, invalidating the documented `/run/user/...` or `/run/host/run/user/...` path] → the `just` recipe that wires `DOCKER_HOST` probes connectivity through the host-execution bridge first and fails with the probe's own actionable error instead of leaving Testcontainers to report an opaque connection error.
- [toolbx and Distrobox expose the host differently, risking drift between two bootstrap paths] → host-integration logic (socket path, alias) lives in one `just` recipe per concern that branches on which container tool is active, rather than duplicated per-tool scripts.
- [`flatpak-spawn` is a Silverblue/Flatpak-runtime-specific tool, not guaranteed by a bare Podman-plus-`toolbox` host] → it is documented as an explicit toolbx-path prerequisite, not assumed; the Distrobox path uses `distrobox-host-exec` instead, which Distrobox provides itself.
- [A contributor's host is missing rootless Podman, a systemd user session, or the `toolbox`/`distrobox` CLI] → the development guide links to upstream installation instructions for the selected host tools. The initial bootstrap does not add a `just` installation requirement.
- [Distrobox's Ryuk bind-mount needs the host-visible socket path, not the `/run/host`-remapped one Testcontainers would otherwise derive from `DOCKER_HOST`] → the Distrobox recipes also set `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` explicitly, rather than relying on Testcontainers to derive the correct mount source on its own.

## Migration Plan

1. Confirm `bootstrap-test-environment` is applied (its markers and Testcontainers fixture are a prerequisite for step 3 below).
2. Add `justfile` recipes for setup (locked `uv` sync, locked `npm` install, `prek install`) and the complete quality gate (the full Prek run, not a hand-picked subset of `AGENTS.md`'s manual list), verifying each against the existing complete-local-quality-workflow requirement rather than against today's partial manual sequence.
3. Add the unit-only `test`/`coverage` recipes and the separate container-backed test recipe(s), each selecting `bootstrap-test-environment`'s existing markers.
4. Add the `Containerfile`, the repository-root `.python-version` pin, and the container-runtime-access recipes/docs.
5. Update `AGENTS.md` to reference the recipes instead of the raw commands, and add a one-line pointer from `README.md` to the setup docs, once the recipes are verified equivalent.
