# Design

## Context

See [proposal.md](proposal.md). Two independent audit techniques are needed because the two dead-code shapes have different signatures:

- **Test-only symbols**: a `src/` function or method never reached by the non-unit suites (integration, e2e, benchmark), which only run against a real MongoDB via `testcontainers` and never call unit-test-only code paths. Running `coverage run -m pytest -m 'not unit'` and reading `coverage report -m --omit 'tests/*' --include 'src/*'` reports these lines as `Missing` directly, keyed by exact line number rather than by symbol name — this sidesteps the name-collision problem a text/grep cross-reference would have (e.g. `_core/manager.py`, `synchronous/manager.py`, and `synchronous/streams.py` each define their own unrelated `close` method; a grep for `close(` cannot tell them apart, but `coverage`'s per-line hit counts can). Confirmed: `CacheCore.lifecycle_state` and `CacheCore.lookup_by_alias` in `src/client_query_cache/_core/manager.py` — production code calls `resolve_alias` + `lookup_identity` separately instead of the combined `lookup_by_alias`, and nothing reads `lifecycle_state` outside `tests/core/test_lifecycle.py`, `tests/asynchronous/test_manager.py`, and `tests/synchronous/test_manager.py` (all `pytest.mark.unit`), so both report 0% coverage under the non-unit suites.
- **Always-true/always-false branches on driver-sourced values**: a conditional in `src/` that guards on the shape of a value MongoDB or pymongo actually produced (change-stream events, index specs, driver return objects), as opposed to a conditional over caller-supplied input (filters, projections, collations) or a caller-configurable driver setting (`CodecOptions`), which legitimately varies and is not in scope. These are checked dynamically: temporarily replace the guard with an `assert` of the branch the code currently treats as the common case, run the non-unit suites (`just test-integration`, `just test-e2e`, and `uv run -- pytest tests/benchmark`) with real MongoDB via `testcontainers`, and if they pass, delete the alternate branch and the temporary `assert` together — the `assert` is a local diagnostic only and is never committed. This planning session tried exactly this on `_wall_time_seconds` in `src/client_query_cache/_core/stream_events.py` — asserting `value.tzinfo is None` only fails 3 tests in `tests/benchmark/stream_cost/test_guard_workload_integration.py` that construct a tz-aware `datetime` by hand, while the integration and e2e suites pass — but the branch is not actually dead: `synchronous/streams.py:153` and `asynchronous/streams.py:157` open the change stream via `self._database.watch(...)`, which decodes `wallTime` using the caller's own `Database`/`MongoClient` codec options, and a caller configuring `tz_aware=True` (a standard pymongo `CodecOptions` setting, already tracked elsewhere in this codebase by `_core/codec.py`'s `codec_fingerprint`) makes `wallTime` come back tz-aware. The non-unit suites passing only shows that _this project's own test suites_ always construct `tz_aware=False` clients — it says nothing about what a real caller's client can be configured to do. This is now this change's canonical counter-example (see the audit inventory's **Skip** row for it): suite-passing after an `assert` proves a branch is unreached by the current suites, not that it is unreachable by any real caller configuration, so each candidate also needs a check of whether it depends on a `CodecOptions` setting (`tz_aware`, `tzinfo`, `document_class`, `type_registry`, `uuid_representation`) before being called dead.
- **Dead fallback keys on driver-sourced mappings**: a `mapping.get(key, default)` call where `mapping` comes from a MongoDB/driver response (e.g., `list_indexes()` index specs, `listCollections` entries) and `key` is expected to almost always be present. `.get()` with a default gives no coverage signal about whether the default is ever actually used, silently masking a dead fallback indefinitely. Converting the call to `mapping[key]` guarded by `try`/`except KeyError` makes the `except` branch a distinct, coverage-tracked line: if the non-unit suites never execute it, that's direct evidence the fallback is dead and the key is always present, and the `except` branch can be removed the same way any other confirmed-dead branch is. This also tends to be faster than `.get()` when the key is present in the overwhelming majority of calls.

Running the non-unit suites requires `testcontainers` (Podman/Docker) and a `.env` with MongoDB connection settings; this sandbox has neither, so the dynamic techniques above are demonstrated but not exhaustively re-run here for every candidate branch or mapping access. Tasks below scope the dynamic audit per source module so each check stays small enough to run and revert independently during implementation, where that infrastructure is available.

## Goals / Non-Goals

**Goals:**

- Remove `src/` symbols confirmed reached only from `tests/` — zero non-unit coverage plus zero production (`src/`) call sites — and the unit tests that exist solely to exercise them.
- Remove `src/` conditional branches (including `.get(key, default)` fallbacks) proven unreachable with real MongoDB/pymongo-sourced values, deleting the dead branch outright with no replacement guard, assertion, or comment.
- Leave every branch that guards caller-supplied input (filters, projections, collations, admitted documents) untouched — those vary by design and are not dead code.
- Close the coverage gap the audit itself surfaces: the non-unit suites (integration, e2e, benchmark) currently measure 88% on `--include 'src/*'`. Every branch this audit confirms real but currently reached only through a caller-configurable `CodecOptions` setting (starting with `_wall_time_seconds`'s `tz_aware` dependency and `without_id`'s custom-decoder dependency) gets an integration/e2e test that actually configures that setting, instead of a permanent, silent exclusion. Target >95% on the same command after this change; higher is better.

**Non-Goals:**

- Do not change any documented public API, cache semantics, or observable behavior for real MongoDB-backed usage.
- Do not add new defensive checks, error handling, abstractions, or permanent `assert` statements while removing dead ones — `assert` is a temporary local diagnostic during the audit, never a committed replacement for a removed branch.
- Do not treat a branch as dead solely because unit tests are its only current coverage without also checking, per the second technique, whether real driver data can reach it — unit-test-only coverage and dead code are different findings requiring different evidence.
- Do not treat a branch as dead solely because this project's own non-unit suites pass after an `assert` replaces the guard — the suites only exercise the client configurations this project happens to construct. Also check whether the guarded value depends on a caller-configurable `CodecOptions` setting (`tz_aware`, `tzinfo`, `document_class`, `type_registry`, `uuid_representation`) that a real caller could set differently, as demonstrated by `_wall_time_seconds` in the audit inventory below.
- Do not treat a symbol as test-only solely because the non-unit suites report it `Missing` — that only proves the current integration/e2e/benchmark scenarios don't exercise it, not that no production code calls it (a real path can simply lack non-unit coverage today). Confirm zero production (`src/`) call sites for each candidate before deleting it.

## Decisions

- **Non-unit coverage to find candidates, a call-site read to confirm each one.** The coverage report (`coverage run -m pytest -m 'not unit'` then `coverage report -m --include 'src/*'`) is a single reproducible command that finds every symbol the non-unit suites don't reach, keyed by exact source line rather than by name. But `Missing` proves only "these suites don't exercise it," not "no production code calls it" — a real path can simply lack non-unit test coverage today without being dead. Each candidate is therefore confirmed by reading its `src/`-wide call sites (excluding its own definition) before deletion, same-named-but-unrelated matches (e.g. the `close` example above) are told apart by opening the call site, and any real production caller found this way removes the candidate from the deletion list. Alternative considered: relying on the coverage report alone — rejected because a `Missing` line only shows the non-unit suites don't reach it, which does not distinguish a genuinely dead symbol from a real production path the current suites simply don't happen to exercise; deleting the latter would remove working behavior.
- **Assert-and-rerun as a temporary diagnostic, plus a `CodecOptions`-dependency check, before deleting for real.** Every always-true/always-false branch candidate is proven by temporarily replacing the guard with an `assert` and running the non-unit suites, but suite-passing alone is not sufficient — as `_wall_time_seconds` showed, a guard can depend on a `CodecOptions` setting no suite in this project happens to configure differently. Only once both the suite run passes and the guarded value is confirmed independent of any caller-configurable `CodecOptions` setting does the committed change delete the branch and the temporary `assert` together. The `assert` never lands in the committed diff — it is scratch scaffolding for the proof, not a permanent contract statement. Alternative considered: reasoning from MongoDB/pymongo documentation alone — rejected because documentation can be incomplete or version-specific, and the project already treats "not derivable from the code" claims as requiring verification (see `CLAUDE.md`'s "Pre-existing Issues" guidance).
- **`try`/`except KeyError` over `.get(key, default)` for driver-sourced mappings.** Where a candidate fallback is on a mapping MongoDB/pymongo produced, convert `.get(key, default)` to direct subscription guarded by `try`/`except KeyError` before running the non-unit suites: an always-uncovered `except` branch is itself the dead-code proof (no separate `assert` needed), and the conversion is kept permanently — it is faster when the key is almost always present, and it keeps the fallback's coverage visible going forward instead of it silently vanishing back into `.get()`'s default. Alternative considered: leaving `.get(key, default)` and reasoning about the key's presence from documentation alone — rejected for the same verification reason as above, and because `.get()` provides no ongoing coverage signal if the assumption ever changes.
- **Scope the dynamic audit to driver-sourced values only.** Conditionals over caller-supplied query documents, projections, collations, or caller-configurable settings (e.g. custom `CodecOptions` type decoders, as in `without_id`'s encode/decode guard) are excluded from the _deletion_ audit even where one arm looks rarely taken in the current test suites, because those arms exist to support legitimate caller variation or configuration, not to guard against an impossible MongoDB response — passing the non-unit suites cannot prove such a branch dead, since the suites don't exhaustively configure every caller-reachable setting.
- **A caller-configurable branch gets a test, not a permanent exclusion.** "Out of scope for deletion" and "acceptable to leave untested" are different claims. Once a branch is confirmed real because it depends on a `CodecOptions` setting, the fix is to add an integration/e2e test that configures that setting for real — `tz_aware=True` for `_wall_time_seconds`, a decode-only `TypeDecoder` for `without_id` — closing the coverage gap the same investigation exposed. Alternative considered: leaving these branches permanently excluded from non-unit coverage since they're "known real" — rejected because an untested-but-real branch is exactly as invisible to a coverage-based dead-code audit as a genuinely dead one, so the next audit (or a future refactor) would have no way to tell them apart without redoing this same investigation.

If a future audit finds a conditional not in this table, classify it the same way before treating it as a candidate: **Skip** if it can be reached by caller-supplied input, an internal cache/lifecycle state check, or a documented real driver failure/miss outcome; **Skip deletion, add coverage** if it depends on a caller-configurable `CodecOptions` setting (real, but not yet exercised by anything other than a unit-test mock); **Audit** (apply the Decisions section's assert-and-rerun-plus-`CodecOptions`-check recipe) only if it guards the shape of a value MongoDB/pymongo produced with no caller-configurable decoding path and no other plausible real outcome.

## Risks / Trade-offs

- A branch guards a value whose shape depends on a caller-configurable `CodecOptions` setting rather than an impossible MongoDB response, so this project's own suites passing after removing it proves nothing about a real caller's configuration (demonstrated by `_wall_time_seconds` and `tz_aware` above) → the audit inventory's `CodecOptions`-dependency check runs before any deletion, and the branch gets a real configuration-variation test (task 3.1/3.2) instead of a silent, permanent coverage gap.
- Closing the coverage gap to >95% could require test infrastructure this audit didn't originally scope for (e.g. simulating a dropped collection or a network partition to reach a real driver-failure branch, rather than a straightforward `CodecOptions` variation) → task 3.3 triages any such remaining gap the same way as the rest of this audit and reports it for a decision instead of quietly accepting a lower number or building open-ended fault-injection infrastructure unasked.
- A branch that looks unreachable today could become reachable if a supported MongoDB version changes a response shape → the assert-and-rerun evidence is captured in the commit body for each removal, and CI continues to run the same non-unit suites on every change, so a future regression surfaces as a test failure rather than as a silently reintroduced guard.
- Deleting a test-only method could remove intentional public API surface → check `README.md`/`docs/` for each candidate before deletion. If a symbol is documented as public API yet has zero non-unit coverage, that is itself a finding (stale documentation or a pre-existing testing gap), not a resolved "keep" — task 1.3 stops and reports it to the user rather than choosing between those causes unilaterally.
- The dynamic audit needs `testcontainers` and a working `.env`, unavailable in this planning session → tasks are scoped so each module's audit is independently runnable and revertible in an environment that has that infrastructure, and no deletion lands without the corresponding suite run.
