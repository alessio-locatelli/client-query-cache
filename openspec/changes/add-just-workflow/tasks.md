## 2. Add the container-based contributor toolchain

- [ ] 2.1 Add a `Containerfile` with a `FROM <image>@sha256:<digest>` base (a tag alone is not immutable - a registry can retarget it to a different image later, which a digest cannot be) ensuring Bash is present (the runtime-access recipes in section 3 are `#!/usr/bin/env bash` shebang recipes, so a minimal base image lacking it would build successfully while every one of those recipes fails immediately) and declaring Node.js, npm, `prek`, `taplo`, `zizmor`, and `just` pinned to explicit versions, setting `UV_PYTHON_INSTALL_DIR` to a non-home path (e.g. `/opt/uv-python`, exported for every shell in the image) before pre-installing the exact CPython patch release via `uv python install <patch>` - `uv`'s default install location lives under the image build user's home directory, which toolbx/Distrobox overwrite with the contributor's own mounted home at runtime, shadowing anything installed there and forcing a network fetch (or a failure without one) instead of using the pre-installed interpreter; verify the `FROM` line names a digest (not a bare tag or `latest`), that a built image exposes `bash`, `uv`, `node`, `npm`, `prek`, `taplo`, `zizmor`, `just`, and the pinned CPython patch on `PATH` each at the pinned version, and that the patch is still resolved without a network fetch when the image's home directory is overlaid by a different mounted home (simulating the toolbx/Distrobox runtime mount).
- [ ] 2.2 Commit a `.python-version` file at the repository root (via `uv python pin <patch>`, matching the same patch task 2.1 pre-installs) - not inside the image, since toolbx/Distrobox mount the contributor's home directory over the checkout path, so anything the image places there is shadowed and never seen by `uv run`/`uv sync` executed from the actual mounted checkout; verify `uv run python --version` run from the mounted checkout (not the image's other directories) reports the pinned patch release, including after the image is rebuilt from the same definition.
- [ ] 2.3 Add `just` recipes to build the image and create a toolbx or Distrobox container from it, and document `just`, rootless Podman, a systemd user session, the `toolbox` or `distrobox` CLI, and (toolbx path only) the Flatpak host-execution bridge (`flatpak-spawn`, backed by the Flatpak portal/session-helper D-Bus service - not guaranteed by a bare Podman-plus-`toolbox` host) as host prerequisites (linking to upstream install instructions for each rather than reproducing them) since none of them can come from an image the host must already build and run before that image exists, and the runtime-access recipes in section 3 need `systemctl --user` regardless of container type; verify each recipe against a running toolbx instance and, where available, a Distrobox instance, starting from a host shell with only that full prerequisite set installed.

## 3. Wire non-nested container-runtime access

- [ ] 3.1 Add a `just` recipe, written as a `#!/usr/bin/env bash` shebang recipe rather than plain `just` lines (by default `just` runs each line of a recipe as its own separate shell invocation, so state such as a detected container type would not survive from one line to the next without one script), that detects the container type, enables the host's `podman.socket` via `flatpak-spawn --host systemctl --user enable --now podman.socket` (toolbx) or `distrobox-host-exec systemctl --user enable --now podman.socket` (Distrobox), confirms that unit is actually active via the same bridge (`flatpak-spawn --host systemctl --user is-active podman.socket` / `distrobox-host-exec systemctl --user is-active podman.socket` - not `podman info`, which is daemonless and can succeed locally even when `podman.socket` is disabled or failed, so it would not actually confirm the service state), and then confirms the container-type-specific path itself is reachable from inside the container with a one-line Python connection attempt against the Unix socket (no Podman client needed, since the design rejects installing one there); failing with an actionable error identifying which of the two checks failed; verify the recipe against a running toolbx instance and, where available, a Distrobox instance, including a case where `podman.socket` is deliberately masked (`systemctl --user mask podman.socket`) beforehand - simply stopping the unit would not exercise the failure path, since the recipe's own `enable --now` step would just start it again before `is-active` ever ran - so that the `enable --now` step itself fails and the recipe's first check reports that failure, and a case where the in-container path is deliberately wrong to confirm the second check catches that.
- [ ] 3.2 Document and add a `podman` alias for interactive CLI use inside each container type (`flatpak-spawn --host podman` for toolbx, `distrobox-host-exec podman` for Distrobox); verify a command issued through each alias executes on the host.
- [ ] 3.3 Add `test-integration` and `test-e2e` recipes, each written as a `#!/usr/bin/env bash` shebang recipe (not plain `just` lines, and not a separately invoked recipe or export - `just` runs a plain recipe's lines as independent shell invocations by default, and separate recipe invocations are independent subshells too, so a `DOCKER_HOST` assignment would not reach the pytest line in either case without one script covering both) - both required, since `bootstrap-test-environment` unconditionally requires an end-to-end tier - that set `DOCKER_HOST` to `unix://` followed by the container-type-specific socket path (the Docker SDK Testcontainers uses parses `DOCKER_HOST` as a URL, so a bare filesystem path is invalid and fails before it ever reaches the socket) and, on Distrobox specifically, also set `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` to the bare host-visible path without the `/run/host` prefix or a `unix://` prefix (`/run/user/$(id -u)/podman/podman.sock` - this variable takes a raw path, not a URL) - Testcontainers' Ryuk cleanup sidecar asks Podman itself to bind-mount the socket into a new container, and Podman resolves that bind source on the host, where the Distrobox-remapped `/run/host/...` path does not exist, so `DOCKER_HOST` alone connects for API calls but Ryuk's own mount still fails without the override - then run `uv run --locked --all-groups -- pytest -m integration` / `uv run --locked --all-groups -- pytest -m e2e` respectively later in the same script (`--all-groups` for the same reason as task 1.4, since `pytest` lives in the `test` group); verify each recipe connects through the forwarded socket and Ryuk starts successfully, from both a toolbx and (where available) a Distrobox container, without starting a nested Podman daemon inside the contributor container.
- [ ] 3.4 Add a `coverage` recipe, written as a `#!/usr/bin/env bash` shebang recipe so its `DOCKER_HOST` assignment reaches the integration-tier line later in the same script, that runs the combined unit-and-integration coverage gate `bootstrap-test-environment` requires for its 100 percent branch threshold, with every step prefixed `uv run --locked --all-groups --` (not a bare `uv run --`: `--locked` for the same lockfile-masking reason as tasks 1.2 and 1.4, `--all-groups` because `coverage`, `pytest`, and `strict-no-cover` all live in the `test` group, not the project's default dependencies; needed at all since `uv sync` creates but does not activate `.venv`): `uv run --locked --all-groups -- coverage erase` first (a previous interrupted or failed run can leave stale `.coverage.*` parallel-mode data that `coverage combine` would otherwise silently fold in, masking branches no longer exercised), then `uv run --locked --all-groups -- coverage run -p -m pytest -m unit` and `uv run --locked --all-groups -- coverage run -p -m pytest -m integration` (the actual per-tier target, not `coverage run -p` alone, which has nothing to execute), then `uv run --locked --all-groups -- coverage combine`, `uv run --locked --all-groups -- coverage report --fail-under=100`, and `uv run --locked --all-groups -- strict-no-cover` (task 1.5 requires this wired in here; a coverage report passing at 100 percent does not by itself catch a prohibited coverage exclusion, which is what `strict-no-cover` checks), setting `DOCKER_HOST` (as a `unix://` URL, per task 3.3) and, on Distrobox, `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE` (as a bare path, per task 3.3) in the same recipe body as task 3.3 since it also exercises the integration tier; verify `just coverage` run twice in a row (the second time after deliberately leaving a stale `.coverage.*` file from an interrupted first run) reports the same result both times, that it fails when an intentionally uncovered reachable branch exists, and that it fails when a reachable branch is hidden behind a prohibited coverage-exclusion comment even while the branch total reports 100 percent.
