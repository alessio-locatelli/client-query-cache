## Context

Generic benchmark execution is part of the test bootstrap. This change starts only after cached reads and stream coherency exist and owns the specialised workload, telemetry, and report contract.

## Goals / Non-Goals

**Goals:** Measure logical cache benefit, stream activity, controlled CPU, and optional direct-path bytes across reproducible workloads.

**Non-Goals:** This change does not claim Atlas or production-server CPU, measure encrypted/compressed wire traffic, or automatically disable caches.

## Decisions

- Keep logical manager counters separate from network and server metrics.
- Use a dedicated local replica-set benchmark topology, resource limits, and client; make unavailable cgroup/runtime evidence an explicit setup failure.
- Compare paired raw and cache variants over idle, read-heavy, balanced, and write-dominant workloads with small/medium/large BSON data. Prime each coherent-cache workload/data-size variant through normal reads, require positive admission and hit counter deltas for that variant before collecting its samples, and retain those deltas with the corresponding report row. Include consolidated-stream workloads with exactly one database-scoped stream serving at least two cached collections in one database, and separately measure writes relevant to the measured cache entries and writes to unrelated collections in that same database, alongside the per-stream invalidation-delivery-lag distribution (`stream-cost-observability`, measured from the event's server `wallTime`, never `clusterTime`, and labelled with its clock-skew limitation) needed to tell whether that unrelated traffic actually delays invalidation. Pair every consolidated-stream conclusion with a matched control run (unrelated writes disabled), each reset to an equivalent starting state (freshly seeded database, empty cache, fresh stream cursor) rather than run sequentially against shared mutated state, run against the same replica-set topology with counterbalanced run order and a pre-registered warm-up phase per run (never a fresh topology per run, which would break the pair's single shared clock-offset calibration across two different primaries), so a lag increase can be attributed to the loaded delivery pipeline as a whole rather than baseline stream/network noise, carried-over state, or asymmetric server-side cache warmth — this isolates "does the shipped pipeline slow down under this traffic," not router-internal serialization time specifically, since no router-stage instrumentation exists to separate that from server or transport load. Because the lag distribution compares the MongoDB server's clock against the benchmark host's, correct it with a minimum-round-trip-time clock-offset estimate against the replica set's current primary (the actual source of each event's `wallTime`; monitor primary identity across the whole calibration-to-pair interval, including between the control and loaded runs, and fail the entire pair on any change rather than apply a stale offset), sampled repeatedly at a fixed cadence rather than only once, so an absolute drift-from-initial check on every sample can catch both a transient clock step a single start/end comparison would miss and gradual cumulative drift an adjacent-only comparison would understate — and ADD twice `total_uncertainty` (the drift-and-its-own-noise upper bound, never the raw drift value alone) to the raw control-to-loaded delta before judging whether the pipeline can be certified healthy (never subtract — this check must use the worst-case delta, or residual drift and its own measurement noise could mask a real regression), since the two runs' residual clock errors can differ from each other by that much even within the accepted drift tolerance, not just cancel out as if the offset were exactly constant, before applying it, and fix the acceptable-lag threshold and an absolute-difference "meaningfully worse" comparison rule (never a percentage or ratio, since the shared offset cancels out of a difference but not a ratio) as workload configuration before either run in a pair executes — never choose them after seeing results, which would let the same distributions justify different conclusions depending on when the threshold was picked. Add a `find`/aggregate workload built from many individually small documents whose aggregate encoded result exceeds the max-entry size — never one oversized document alone, which would only exercise single-document rejection — so the cost of materializing many documents before their aggregate crosses the limit is measured directly rather than inferred from documents that fit. Since incremental abandonment isn't implemented and the shipped encoder has no observable intermediate state to checkpoint (it encodes the complete result in one call), determine the crossover prefix empirically — a bounded search invoking the shipped encoder's real envelope wrapping on successive candidates, not by summing individual document sizes, which omits array-wrapper and envelope overhead — then time the same unmodified shipped encoder invoked repeatedly on that prefix and repeatedly on the complete result, aggregating each set by a pre-registered rule rather than trusting a single sample of either (scheduling/GC/allocator noise can otherwise flip which side of the threshold the comparison lands on) — never a separate hypothetical incremental serializer, and never cursor fetch or transport cost, which either strategy pays regardless. This comparison is only a cheap triage signal, not a proven bound on a real incremental strategy's cost in either direction — a different encoding approach could use cheaper or more expensive primitives than the shipped bulk one-shot encoder on a smaller input: a below-threshold result supports only a cost-benefit judgment that prototyping is likely not worthwhile (not a proof it would fail), while an at-or-above-threshold result justifies a follow-up change to actually build and measure a prototype before deciding to ship it. Only the prototype's real measured cost, never this triage signal, can conclusively decide the question — the router decision above genuinely has a conclusive branch because it measures the shipped pipeline directly, but this measurement never touches a real incremental strategy at all, so neither of its branches is conclusive proof. Record per-variant latency distributions with cache-outcome labels alongside aggregate timing for operation-bearing variants; represent idle variants with zero operations and an explicit no-latency-samples marker.
- Use an optional dedicated TCP proxy only when TLS, compression, discovery, and shared connections are disabled; call its result path bytes, not universal wire bytes.
- Upload reports in opt-in CI without timing regression gates.
- This change's evidence directly gates two decisions deferred elsewhere, though the two are not equally conclusive. For `implement-change-stream-coherency`'s single serial per-database router: the matched-control consolidated-stream lag distributions measure the shipped delivery pipeline directly (server, transport, and router combined), so a "no problem" conclusion is genuinely decidable from this change's measurements alone, subject to one disclosed, unverifiable assumption this benchmark's periodic calibration sampling cannot rule out — that no clock step-and-revert occurred entirely between two consecutive calibration samples during the pair, since an undetected step's magnitude (unlike its possible duration) has no bound this instrumentation can establish. Closing the question requires both a control-to-loaded delta that isn't meaningfully worse AND both runs' own absolute lag meeting the pre-registered threshold, since a flat delta between two already-saturated runs is not sufficient on its own — while a failure of either check only justifies opening a follow-up change to add router-stage instrumentation before choosing a specific remedy. For `implement-cached-read-api`'s full-materialization `find`/aggregate admission: the oversized-result workload's prefix-versus-full-result encoder-invocation comparison never touches a real incremental strategy at all — it invokes the same shipped one-shot encoder on two differently-sized inputs, which bounds neither direction of what a genuinely different incremental encoding approach would actually cost — so neither a below- nor an at-or-above-threshold result is conclusive; a below-threshold result only supports a cost-benefit judgment that prototyping is likely not worthwhile, and an at-or-above-threshold result only justifies opening a follow-up change to build and measure a real prototype, whose measured cost is what actually decides the question. Both changes ship their simple default as-is and are expected to already be archived by the time this evidence exists, so both decisions are recorded in this change's own `design.md` once made, never by editing an archived change's design doc. Recording both decisions is tracked as tasks in this change's `tasks.md`, so resolving them cannot be silently skipped when this change is archived.

## Evidence-gated decisions

- **Serial database router (task 5.1):** Keep the shipped single serial per-database router for the pre-registered consolidated-stream workload. All three counterbalanced control/loaded pairs independently met the 0.5-second absolute 95th-percentile lag threshold in both runs and the 0.1-second uncertainty-adjusted delta threshold. The [decision evidence](../../../reports/stream-cost/v1/decision-evidence.report.v1.json) records each pair's clock calibration, corrected lag windows, confidence intervals, and overlapping unrelated-write count. This measures the complete delivery pipeline under this local workload; it does not isolate router execution time. The healthy conclusion depends on the unverifiable assumption that no clock step and reversion occurred entirely between consecutive calibration samples.
- **Oversized-result admission (task 5.2):** Keep full-materialization admission as shipped under a cost-benefit judgment; do not invest in an incremental prototype based on this triage result. The same [decision evidence](../../../reports/stream-cost/v1/decision-evidence.report.v1.json) records a 0.000445-second median encoder-invocation savings against the pre-registered 0.005-second minimum. This comparison does not bound a real incremental encoder's cost in either direction, so the judgment may be revisited with a prototype measurement if the workload or economics change.

## Risks / Trade-offs

- [Environment noise corrupts conclusions] → Record environment and samples, control resources, and avoid cross-host thresholds.
- [Projection removes an event needed for invalidation] → Test every event type and resume path against functional coherency before measuring.
