# Design

## Context

See [proposal.md](proposal.md) for motivation and scope. The evaluation's observable obligations and acceptance gates live in the [delta spec](specs/process-local-cache-evaluation/spec.md).

Planning inspected clean branch `rewrite_to_rust` at `419b54d077e7c635d9661b7161998931116cd716`, equal to local `main`. The synchronous and asyncio managers instantiate `CacheCore` directly before creating their stream coordinator. The core's optional `PayloadStore` changes value storage only; namespace state, keys, generations, and LRU bookkeeping stay in Python. It therefore cannot exercise the proposed ownership boundary by itself.

`lookup_identity_encoded`, `lookup_namespace_encoded`, and `lookup_find_encoded` perform separate storage probes, validity checks, LRU touches, and statistics updates. Find compatibility also consults a family index. `CacheCore` is used by the shared owner as well as local managers, so replacing it globally would affect an unrelated execution path.

The [process-memory results](../../../reports/process-memory/summary.md) date from October 10–11; the [cursor study](../../../reports/cached-read-cursors/summary.md) dates from October 5. Neither establishes current native-core gains. The [completed Rust encoding correction](../../../reports/shared-worker-cache/current-costs/rust-encoding.md#final-review-correction-and-acceptance) concerns shared-key preparation and has a specifically approved resource trade-off. That approval does not carry into this experiment.

## Goals / Non-Goals

The design goal is one native owner for resident keys and metadata, evaluated without a duplicate Python ownership graph. Python retains PyMongo integration, result codecs, request classification, cursor capture, stream supervision, and stream-cost telemetry. This keeps the experiment's causal question narrow: what does moving storage and its associated bookkeeping together actually save?

The existing [cache-core](../../specs/cache-core/spec.md), [cached-read-api](../../specs/cached-read-api/spec.md), and [change-stream-coherency](../../specs/change-stream-coherency/spec.md) specifications remain the semantic authorities. The native local core does not take over the shared owner's observer/payload publication integration.

## Decisions

### D1. Integrate in the library from the first candidate

Add the native owner to `native/shared-index` and its adapter to `src/client_query_cache/_core/native.py` from the first candidate. A temporary nondefault Cargo feature, provisionally `local-cache-prototype`, can isolate candidate builds during acquisition. Put only acquisition orchestration and disposable spikes under `research/native_process_local_cache/`.

During comparison, select the core constructor privately before manager/coordinator creation in a fresh child; restore selection during fixture teardown in tests. Both paths report their selected implementation. The shared owner continues to use its existing publication-capable core explicitly, so local integration cannot switch it incidentally.

The project has no real users, and the user prefers a clean ownership model over compatibility machinery. Core and capture types may change where this simplifies native integration; do not preserve exported core types or private capture-field annotations solely for compatibility. Keep the documented sync/async read behavior, codecs, and consistency guarantees. Use backend-owned capture handles, with release delegated to their owner even after namespace recreation or core close, rather than retaining a Python `NamespaceState` graph for native execution.

When the candidate qualifies, make both ordinary managers construct the native core, include its bindings in the regular wheel, and remove the temporary feature gate and comparison-only constructor hooks from normal runtime paths. Keep the reference needed by the shared owner and acquisition; do not add a supported local backend selector or silent native-load fallback. Task 4.2 must qualify this final construction/build path, including import and startup costs.

| Existing crate plus library adapter, selected above     | Reuses the actual wheel, binding, and facade integration | Candidate isolation and final default path need verification                      | Tasks 2.2 and 4.2                                                 |

The existing crate's Linux dependencies remain in effect. This layout makes no new portability claim.

### D2. Move ownership and validity decisions together

The native owner holds the resident-key index, entry tokens, namespace/identity generations, in-flight capture references, aliases, find-family references, LRU links, budget accounting, and ordinary cache statistics. The adapter translates existing core calls and snapshot types; it must not retain parallel Python `CacheEntry`, `NamespaceState`, or key indexes for the native path.

Use a GC-tracked native identity handle to own an identity's original Python key and trace its aliases. Captures hold that handle strongly; the native index holds it weakly while no identity value is resident, and resident values retain it strongly. This permits key/capture cycles to be collected while the core stays open. Alias comparison snapshots pin the handle, and reclamation validates its non-reused token. Visit each owned Python reference once through its actual authority, and release Python references outside the mutex. The handle and weak-reference allocations are part of the measured candidate's resource cost.

Use stable tokens to distinguish displaced entries and captures from later entries at reused locations. Hold immutable encoded BSON through owned references to the existing Python bytes where practical, so a hit can transfer a reference without introducing a payload copy. Continue using the established Python codecs to encode/decode values. Preserve current entry weighting, including documented alias accounting, rather than mixing an accounting correction into the experiment.

Each lookup performs key selection, generation/availability validation, LRU update, and outcome accounting through one native binding call, returning owned bytes or a miss/bypass outcome. That call can release and reacquire the mutex for D3 comparisons; it commits against the revalidated version. Admission similarly validates a captured token and publishes all associated indexes under one authority. Snapshot, invalidation, availability, namespace lifecycle, capture release, and close complete the adapter surface required by the managers and coordinator.

Start with safe Rust containers and one per-core mutex. D3 defines the callback protocol; release displaced Python references after leaving the mutex. Keep the interpreter attached while transferring Python references, and hold no exclusive PyO3 borrow across a callback that can reenter the owner. Do not introduce lock-free reclamation or release the interpreter merely to accelerate short calls.

An LRU-only rewrite retains the other Python maps and crossings, so it would not answer this design's question. A BSON serializer or cursor rewrite changes a different dominant cost. Both alternatives are excluded without further research. Whether a coarse native lock becomes a bottleneck remains a measured question in task 3.2; a contention-driven redesign requires an amended design and user decision rather than an automatic second architecture.

### D3. Preserve the full process-local key domain

The local canonicalizer accepts hashable Python leaves, and codec fingerprints contain Python identity semantics. The shared wire format intentionally rejects some local keys, so it cannot be the correctness authority for the replacement.

Task 2.1 evaluates at most two representations: compact native ownership of the existing tagged canonical nodes with Python-owned opaque leaves, and reference-preserving Python keys with native entry metadata. The first is preferred because it can remove the large retained tuple graph. The second is a bounded comparator if compact ownership cannot preserve equality; it offers a smaller potential memory gain. Both use the existing normalization rules rather than introducing new query equivalences.

The feasibility result must demonstrate equivalent mixed native/Python equality, not just native/native comparison: opaque leaves can compare equal to values handled natively. Preserve hashing collisions, numeric identity normalization, numeric discriminator distinctions, embedded order, codec-registry identity, and exception propagation. Any interning table must release entries with the last resident/capture owner; unique historical probes cannot grow it indefinitely. Never key a cross-request memo by mutable input identity.

Use a versioned bucket snapshot for operations requiring Python equality. Under the mutex, pin owned references to the candidate keys/values and capture the bucket revision, stable entry tokens, and relevant generation/availability versions. Unlock, compare the pinned keys using Python semantics, then lock again. Commit only if the compared bucket and all validity versions still match. Otherwise discard the pending decision and retry against current state. Include bucket insertion/removal in revision changes so a negative comparison cannot miss a concurrent insertion; use non-reused versions to prevent ABA after replacement or namespace recreation.

Python callback exceptions propagate after releasing pins outside the mutex, with no pending lookup statistics or LRU update committed. Mutations performed by callbacks remain effective. Task 2.1 must demonstrate finite reentrant mutations, deliberate collisions, concurrent invalidation/replacement, a concurrent insertion after a negative comparison, and exceptions. The same protocol applies to equality needed by admission and alias operations. Do not build the full adapter until the spike demonstrates the version compared outside the lock is the version whose validity decision commits.

These representation costs and the protocol's behavior cannot be established without a spike. Record the selected layout and synchronization evidence in the evaluation registration before building the complete adapter. If neither representation is sound, retain the failing cases and conclude infeasibility; do not silently narrow supported reads. Comparing under the mutex risks callback deadlock; comparing outside it without version revalidation risks stale decisions. Both are rejected without further research. The existing Python core is the concrete no-change alternative and needs no separate implementation.

### D4. Reuse the existing acquisition tools

The canonical protocol belongs in `reports/native-process-local-cache/plan.md`, with the conclusion in `reports/native-process-local-cache/results.md`. Raw files go under a session directory in `/tmp/agents/`. Extend existing harness selection/output fields only where required, keeping new selection out of ordinary library code.

The public harness currently has four workers and no candidate-core selection or memory-study query shapes; the memory harness likewise selects only direct/cached. Extend their private selection and reuse the memory study's document/filter builders for the added public-read cells. Verify actual encoded size rather than setting a payload flag to 59, and keep any refactored builders shared with the memory harness. Single-process fresh-child memory checkpoints remain the density comparison; the public harness supplies application-path runtime evidence.

Use installed release wheels for frozen `main`, the candidate-build reference control, and the selected native core. The candidate-build reference distinguishes packaging/import overhead from storage effects; frozen `main` remains the cost baseline. D5 adds the final ordinary-wheel comparison to that same frozen baseline. Match imported artifacts and avoid editable-build contamination. Four-worker memory observations must not be substituted for single-process density figures.

Register five counterbalanced revision blocks, both models, and the target metric before timing. Use 4,096-byte document payloads for identity/16-document sorted reads; the memory harness records actual BSON size for its larger documents. Select complete hot catalogues that fit both implementations and disjoint cold keys. CPU covers readers plus their supervisors for the measured completed work; MongoDB is separate. Observe admission completion and transient peaks in an additional untimed resource window when work outlives a read barrier.

Register the small-result controls at the same time, including P50/P95/P99, CPU/read, throughput, exact results, and hit/miss/bypass counts for both filters. Match entry/BSON residency for hot runs and the starting state and eviction trajectory for cold runs. These cells are mandatory regression controls even when another workload supplies the primary gain; longer keys cannot be evaluated for memory alone.

For each small-entry/long-key memory checkpoint registered as eligible to satisfy the memory gate, run its public-read controls at that checkpoint's actual resident-entry count, BSON budget, and occupancy. The existing pre-eviction warm checkpoint follows 64,000 distinct reads with a 4 MiB budget; include any warmup/alias entries in the observed count rather than equating requests with resident entries. A post-eviction memory claim instead needs controls at its measured post-eviction occupancy. Record entry count, `used_bytes`, budget, occupancy ratio, and catalogue coverage before/after each timed window. Warm controls traverse that resident catalogue; cold controls use disjoint keys from the matched starting checkpoint and retain the registered admission/eviction trajectory. A 4,096-key control cannot qualify a memory claim made at a larger occupancy. To keep the matrix bounded, predeclare one eligible memory checkpoint/filter if only one additional occupancy control is needed; every other checkpoint remains descriptive evidence.

The existing four-worker topology measures independent cores. Add a registered topology with one worker process, one synchronous `CacheManager` and caller-owned client created before reader threads, and 1-thread/4-thread reader cells. Reuse the identity dataset, timing/counter collection, and existing writer machinery; the writer stays outside the reader process. Synchronize reader and writer start, fix the measurement duration and offered read/write schedules before acquisition, and update identities within the readers' catalogue through MongoDB. Verify that the same manager processes invalidations while reads are active: completed writes alone do not establish overlap. Register the expected invalidation/progress evidence, cache-outcome accounting, and tail-lag treatment before timing; an interval with no processed invalidation is invalid. Compare reference/native throughput, P50/P95/P99 latency, CPU per completed read, and actual hit/miss/bypass counts under equivalent initial residency, concerns, duration, and offered load. Report completed writes, processed invalidations, and lag separately so different effective write pressure cannot masquerade as a lock-speed improvement. This performance control complements task 3.2's ordering tests and is mandatory again for the final ordinary wheel.

Register a bounded shared-path control before candidate timing because the local owner shares the `_shared_index` binary with the existing shared implementation. Compare the final ordinary wheel against frozen `main` using `benchmarks.public_shared_cache` with `--paths shared --workloads hot`: identity reads over 1,024 keys and sorted find over 128 groups of 16 documents, both execution models, four workers, 4,096-byte payloads, and no writer. Keep the harness's shared budget/arena/slot settings identical, verify equal complete residency, and reject unexpected misses, bypasses, origin reads, or owner selections during timed warm reads. Report P50/P95/P99, throughput, and worker-plus-owner CPU/read. This is a regression control, not an additional improvement target or a repeat of the historical shared-cache matrix.

In separate fresh processes, measure public-library import wall/CPU cost; for the shared topology also measure startup wall time through owner readiness and all worker attachments/metadata readiness before result warmup. Exclude fixture seeding/builds from these intervals and account for startup CPU across owner and workers. Capture per-process RSS and group PSS at startup readiness and after the matched catalogue is resident, counting mapped pages proportionally and excluding MongoDB/collector memory. Reuse the existing harness, process collectors, and normal shared construction; extend only the missing phase observations. Use D4's matched repeated blocks and uncertainty policy for these startup/resource probes and warm reads. An unchanged owner algorithm does not waive the regression gate for a larger or differently initialized native binary.

Use per-block relative changes rather than treating individual requests as independent replications. A claimed threshold must be met in every valid block for the registered target; report the median and full block range. Mixed directions or coarse counters are inconclusive. One additional five-block acquisition is allowed to resolve a named uncertainty; retain both cohorts separately. This rule is deliberately conservative for a prototype, rather than a general statistical claim.

The acquisition plan allows one attributed correction after the initial candidate comparison. Stop after that correction and its registered remeasurement, or sooner for a semantic blocker. Do not widen the workload set to search for a favorable result. Synthetic core-only loops can explain costs but cannot replace the delta spec's complete-operation gates.

A fresh custom benchmark framework could provide tighter attribution but would add its own validation burden. Existing tools already cover the selected workloads; no further tool search is necessary. Their required extensions and whether process counters resolve short hit windows are handled by tasks 1.1 and 3.1.

### D5. Complete or remove the native integration in this PR

The results report maps every candidate case to a conformance result and the registered gates. Once a candidate qualifies, continue through task 4.2 in this branch and PR, amend these artifacts for any necessary in-scope integration details, and complete the documentation with the implementation. A report or temporary feature build is an intermediate checkpoint, not a successful completion. No production follow-up issue is required. A concrete blocker or consequential design choice outside the agreed boundary still requires a user decision.

Before measuring a candidate, commit its exact native source, library adapter, harness integration, build settings, and registered commands. Before removing rejected code, publish and preserve that immutable commit in the PR history; the report links the full commit URL and reproduces from that checkout. A later revert/removal commit preserves reachability. Do not squash/rebase away measured candidates; if history must be rewritten, first retain their commits under a durable published ref and verify they can be fetched independently. Raw results remain untracked.

Remove unsuccessful runtime code and private selection hooks before finalizing a negative result. For a qualifying result, qualify the final regular wheel and ordinary manager construction against frozen `main`, including all D4 local and shared-path controls and the existing-test timing set; passing a feature build alone is insufficient. This final integration acquisition is mandatory and separate from D4's bounded candidate-tuning allowance. Update the architecture guide, review affected public guides and Context7 rules, and remove obsolete local-only implementation paths without disturbing the shared owner's still-used reference code.

## Risks / Trade-offs

- Compact keys can lose Python equality semantics → Complete D3 before general implementation; any difference blocks qualification.
- A native lock plus Python callbacks can deadlock or reenter → Keep callbacks and reference destruction outside the native critical section; exercise real callback and concurrent cases.
- A single mutex can serialize stream invalidation and reads → Measure contention and processed-invalidation ordering rather than infer scalability from single-thread loops.
- A lean adapter can accidentally recreate metadata ownership → Audit retained Python/native graphs alongside process memory, including aliases and captures after eviction/close.
- Fresh-process allocator behavior can resemble a leak or saving → Compare populated, evicted, closed, and repeated lifecycle checkpoints using the existing memory methodology.

## Migration Plan

Applications keep their existing manager construction and configuration. A qualifying final wheel uses native local storage with Python stream transport and codecs; cached values remain ephemeral. An unqualified result restores the reference construction before completion. Reverting the integration commit returns the library to that construction without a persisted-data migration.
