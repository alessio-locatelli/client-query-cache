# Spec Delta

## ADDED Requirements

### Requirement: Event-loop comparisons isolate the loop choice

Asynchronous loop comparisons SHALL use identical application work, package builds, data, concurrency, telemetry, database resources and measurement instrumentation. Repeated independent runs SHALL alternate loop order and report operation latency distributions, throughput and scoped CPU costs for process-local and shared managers, including hot hits and cold misses. Standard asyncio SHALL remain an available baseline.

#### Scenario: A paired workload completes

- **WHEN** both loops complete a registered workload
- **THEN** evidence includes per-run results, paired variation, versions, workload configuration and validated cache outcomes, with warmup and startup distinguished from measured operations

#### Scenario: A result is invalid

- **WHEN** a run fails validation or encounters a behavioral difference
- **THEN** it cannot support a performance claim, its failure remains visible, and its root cause is investigated before adoption

### Requirement: Loop resource comparisons include completed admissions

Shared-owner and group CPU comparisons SHALL include all admission work generated by measured reads through verified completion, including rejected or evicting admissions when present. Evidence without that completion check SHALL NOT qualify a CPU saving or establish absence of a CPU regression. Instrumented resource results SHALL identify their telemetry setting and SHALL NOT be presented as measurements of a different configuration.

#### Scenario: Foreground reads finish before queued work

- **WHEN** measured reads return while shared admissions may remain queued
- **THEN** the resource interval continues through verified admission completion, with foreground latency and drain time reported separately

#### Scenario: Default-path timing cannot verify owner completion

- **WHEN** a telemetry-disabled timing run has no admission-completion verification
- **THEN** its owner and group CPU results are labelled incomplete, and a separate verified resource comparison is required before adoption

### Requirement: Event-loop adoption follows demonstrated benefit

Benchmark integration SHALL be selective and require a reproducible benefit beyond observed noise without unacceptable regressions. Regression and inconclusive outcomes SHALL retain the affected standard-loop configuration. Decisions SHALL record negative results, uncertainty and reproduction commands in the PR description; raw results SHALL remain untracked. Deferred necessary work SHALL have a GitHub issue.

#### Scenario: Only some workloads improve

- **WHEN** one workload benefits while another regresses or remains inconclusive
- **THEN** adoption is limited to the qualifying workload and the decision explains both outcomes

#### Scenario: Workers execute one request at a time

- **WHEN** measurements use sequential foreground reads within each process
- **THEN** adoption conclusions and documentation recommendations identify that workload and do not claim a benefit for concurrent foreground requests on one loop

### Requirement: Optional application guidance reflects evidence

Documentation SHALL recommend optional uvloop use only when measurements demonstrate benefits, naming the applicable workloads and limits. A recommendation SHALL include `asyncio.run(..., loop_factory=uvloop.new_event_loop)`. If only compatibility is verified, guidance SHALL state that existing uvloop applications may continue using it without claiming acceleration. The library SHALL neither require, install nor configure uvloop.

#### Scenario: Compatibility holds without a resolved speedup

- **WHEN** both loops pass compatibility checks but timing differences remain within noise
- **THEN** documentation makes no optimization recommendation
