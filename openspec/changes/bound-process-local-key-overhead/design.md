# Design

## Context

See `proposal.md` for motivation and the delta specs for the public contract. Current production process-local managers construct `LocalCacheCore` through `_core/native.py`. In `native/shared-index/src/local_cache.rs`, `State::put` charges encoded payload length; `Body::Alias` has zero BSON weight. The Python `CacheCore` remains the shared coordinator's core and the native implementation's differential reference.

The native owner already has generation-aware residency, namespace indexes and deferred destruction outside its mutex. Its alias ownership intentionally can outlive the last resident value while a capture is active (`tests/core/test_native_owner.py::test_capture_keeps_alias_alive_after_last_entry_eviction`). The safeguard must account for those aliases rather than assume that value eviction removes them immediately.

The active `migrate-remaining-hotpaths-to-rust` change proposes replacing shared-owner bookkeeping. This plan targets the current checkout; neither change depends on the other. If that work lands first, integrate at the resulting residency seam and keep one authoritative accounting implementation per core, preserving this change's contract and differential coverage.

## Goals / Non-Goals

The design extends current ownership and inspection seams; it introduces no persistent state, background accounting task or new dependency. Shared managers continue to construct their core with the optional limits disabled. Their configuration adapters and group-observation serializer still need the budget-name update.

Transient identity reservations and active cursor snapshots remain governed by their existing lifecycle. Bounding concurrent requests, arbitrary objects referenced inside scalar keys, or allocator high-water marks would require a different contract.

## Decisions

### D1. Separate cardinality from per-key charging

Use the two controls defined in the cache-core delta. Together they address many small values and large predicates without estimating every internal Rust/Python allocation. Their independent optionality preserves existing admission by default; finite defaults would select new cache-hit behavior without current native-workload evidence.

An entry-only cap has constant admission work but leaves a few enormous predicates unchecked. A key-only cap leaves arbitrarily many tiny records. A total estimated metadata budget can allocate capacity more flexibly but couples policy to representation details and requires more mutable accounting. These alternatives need no further research for this scope; actual overhead and footprint of the selected combination remain unknown until D5, implemented by task 4.1.

### D2. Charge canonical objects at prospective publication

Implement one shared sizing operation used by both cores, applying the charge definition in the delta. Use `sys.getsizeof` for shallow sizes, an iterative tuple walk, and a temporary identity set scoped to one record. Identity value roots include the canonical identity and read shape; namespace values use the discriminator; aliases use their canonical alias tuple and resolved identity. Exclude canonical tag singleton identities centrally rather than duplicating a tag list across cores. Stop early once the limit is exceeded.

Invoke sizing only after ordinary eligibility/generation checks make publication possible, before mutating residency, and outside all owner locks, including D3's Python transaction: custom hashable scalars are already accepted by canonicalization and can define a raising or reentrant `__sizeof__`. A sizing exception becomes the specified decline; it must not escape into native read delivery. Recheck generations/revisions after callbacks before publication. Reuse each computed decision across internal retries. Do not memoize arbitrary caller-owned scalar objects across calls because their lifetime and mutable size are not controlled by the cache. For count-enabled composite admission, skip pair sizing when its two-record minimum is impossible; otherwise size its identity before its dependent alias. Size the namespace candidate only if fallback is needed. Record only the final policy decisions under D4.

The charge is intentionally representation-dependent. It includes tuple slots and shallow scalar storage, not recursive attributes of arbitrary objects. Aliased subtrees are counted once per record and independently across records; no global ownership map or reference-count estimates are needed. No aggregate key-bytes counter is proposed.

Serializing a key merely to measure it adds copies and rejects otherwise supported custom scalars; walking all GC referents can enter application graphs and changes the guarantee substantially. Folding sizing into canonicalization could reuse a traversal on misses but adds work to warm reads and changes every preparation interface. Neither alternative needs research for this change. D5 measures the chosen miss-only traversal, including the disabled fast path.

### D3. Reclaim through existing residency operations

#### Python transaction and lock order

`LockOrderGuard` forbids overlapping namespace and LRU sections. `_admission_section` already holds the manager-wide `_availability_lock` (an `RLock`) through LRU insertion, but releases it before eviction cleanup and final publication. Reuse that lock as the outer count-transaction gate rather than adding another global mutex. With `max_entries` enabled, acquire it at the mutation entry point, before lifecycle, registry, namespace or LRU locks; release all inner locks before leaving it. Enter namespace and LRU sections sequentially, never together. Internal helpers reuse the owning transaction. Never acquire the gate while holding a namespace/LRU section; extend the guard to reject that inversion before blocking.

Hold this gate through count planning, LRU mutation, `_process_evicted`, alias pruning and `_finalize_put`, including rollback. Every path that can remove records must participate: direct and composite admission, stale-alias and namespace-entry discard, write invalidation, clear/create/drop/release, capture release that prunes aliases, and close. Capture state must carry the enabled transaction context so `IdentityCapture.release()` enters it before its namespace lock. Collect registry references under `_namespaces_lock` and release that lock before entering namespace/LRU sections. Capacity snapshots use the gate while reading both components. Warm touches need no count transaction, but must participate in the LRU revision check below.

For count-enabled Python cores, maintain an LRU revision advanced by actual recency changes and value mutations. Read the revision with the tentative victims in one LRU section, then inspect alias ownership in separate namespace sections. Before any destructive change, reacquire the LRU section and compare that revision; if it changed, discard the uncommitted plan and replan without repeating sizing or recording declines. Validate and commit the value removals/insertion within that same LRU section, preventing a touch between final victim validation and eviction. Finish planned alias unlink/publication and namespace bookkeeping after releasing the LRU section while retaining the count gate. Reserve the matched identity through that interval so pruning cannot remove its generation state. Native victim planning and mutation remain in one native mutex section. Task 3.1 includes a coordinated warm promotion between planning and commit; both cores must preserve the resulting LRU order.

Keep observer ordering from `tests/core/test_residency.py`: `removed` and payload release are synchronous LRU-local hooks, and `admitted` and invalidation hooks remain namespace-local. They do not acquire the count gate themselves. These internal hooks retain their existing prohibition on recursive core mutation while a storage section is held; the inversion guard must fail promptly instead of allowing a callback to block acquiring the outer gate. Do not move removal notification after publication or payload reuse. The explicitly reentrant `namespace_released` callback runs after the transaction and all inner locks are released, with the namespace still reserved as untracked until notification finishes; its final registry removal must tolerate reentrant close. Run sizing and encoding callbacks before the transaction, then revalidate capture/lifecycle/availability. Retain detached keys, entries and identity state until after the gate is released so their last-reference finalizers cannot execute inside it.

The native owner continues to use its existing mutex, revision retry and deferred destruction; it does not acquire a Python gate. When the count limit is disabled, the Python core keeps its current transaction boundaries. A separate transaction mutex would add another lock-order relationship without providing isolation beyond the existing global admission gate. A reservation ledger would permit more concurrent writers but needs pending-slot, cancellation and retirement states across both stores. Neither alternative needs a prototype for this scope. Enabled-path contention and complete callback/lock coverage remain unknown until tasks 3.1 and 4.1.

#### Alias membership and reclamation cost

Only with the count limit enabled, maintain a live-only insertion-order alias index so victim selection does not scan identities or retain historical tombstones. Avoid adding links to every resident row when an enabled-only alias structure suffices. Update it on displacement, invalidation, pruning, stale-alias removal, namespace release and close. Derive native alias count from live state rather than keeping a second independently updated total.

Replace Python `IdentityState.alias_keys`'s copy-on-write `frozenset` with a lazy mutable set: no set while empty, create on the first alias, mutate only under the namespace lock, and release the set after removing its last member. Whole-identity invalidation iterates the membership once and then drops it. This preserves the existing empty-storage rule while making membership addition/removal amortized constant-time for fixed-cost keys and full reclamation linear in alias count. Audit every iterator before introducing in-place mutation; detach or snapshot only where iteration and removal overlap, not on every operation. Retire detached membership and alias references until after the outer transaction when enabled. This representation fix also applies to the disabled Python path, so its cost must be measured.

Copy-on-write membership keeps snapshots immutable but copies all surviving aliases for each single removal, producing quadratic churn. Always allocating a mutable set avoids copying but adds empty storage to unaliased identities. The lazy representation avoids both costs; no further design research is required. Task 4.1 measures full publish/remove sequences at increasing cardinalities on both cores; constant-time victim selection alone is not the acceptance evidence.

#### Capacity planning and composite admission

Check key decisions and prospective count deltas before destructive mutation. A declined key must not evict existing data. Replacements subtract only the exact displaced record. Reclaim aliases to relieve count pressure, then use the value LRU for remaining pressure. An alias alone cannot displace a value. For ordinary BSON-only eviction, retain the existing policy.

For `admit_unique_key_match`, use the delta's pair-and-fallback policy only when `max_entries` is configured. The pair references one identity payload, with the usual BSON charge, and does not create a namespace payload. Keep the current three-record publication policy when the count limit is disabled, including with a key limit alone; configured key checks can still decline its individual candidates. Do not let a key-only configuration silently enable the new admission policy.

Under the owner transaction, validate and pin exact matching identity, alias and original-namespace records against the capture. Credit only actual replacements and reuse current matching identity/alias records. Tentatively retire an exact redundant namespace record as part of a successful pair replacement; never credit a newer or merely equal-looking record. Determine the normal identity-value-alone admission plan, including alias-first count reclamation, byte pressure, normal LRU victims and alias pruning caused by those victims. Then test the extra alias against the resulting net occupancy. Additional alias reclamation is allowed, but the pair must not add unrelated value victims beyond that value-alone plan. Reusing an existing alias does not exempt it from this comparison: protecting an alias that value-alone admission would reclaim must not force an extra unrelated-value eviction. Plan only over needed victims and ownership links, without copying the full cache.

Commit both selected pair components together, publishing the alias after its identity value is valid and reserved. A rejected pair changes neither residency nor recency. If namespace sizing is still needed, leave the transaction without mutation, size it outside locks, and reacquire the transaction to revalidate generations and recompute feasibility against current occupancy. Prefer the pair if it has become feasible; otherwise apply ordinary single-value admission to the namespace fallback. That fallback does not commit a leftover identity candidate or alias from the rejected plan. Existing unrelated records may be evicted for that one fallback value under the ordinary rules. An already resident identity may remain independently; its existence alone does not make the composite admission successful. Counts are never selected from the configured number alone: replacement, shared payload accounting, captures, reclaimable aliases and concurrent admissions determine the final plan.

The sync/async `_resolve_unique_key_read` currently calls `discard_namespace_entry` before composite admission. With the count policy enabled, move that exact-record retirement into the transaction instead, including stale-alias displacement only when a valid replacement plan commits. Preserve the existing count-disabled facade path. A namespace fallback must also be reachable when an alias exists but its read-shape-specific identity value misses: try the identity path first, deferring its miss recording using the same pattern already supported by namespace lookups; on failure try the namespace fallback, then record one final miss only if neither serves the read. Identity-pair warm hits require no additional namespace probe. Reverify the original predicate on an origin miss as today. Update the cached-read-api delta because its current first-match and resolved-alias requirements assume both value records or an unconditional origin read after an identity miss.

This policy lets one payload serve original unique-key and matching identity queries when an alias also fits. Its namespace fallback keeps the original query cacheable with one slot. Compared with always retaining both values, it saves a duplicate BSON charge but relies on alias resolution for the unique-key hit; alias churn can therefore reduce reuse. Always admitting only the pair is simpler but fails the one-slot use case. Namespace-first admission serves the original query without an alias but spends capacity on two values before reaching equivalent identity reuse. Evicting an extra unrelated value to force a pair can discard a hotter result for an optional acceleration. These alternatives need no further policy decision; actual trade-offs under churn and unrelated writes remain unknown until task 4.1's policy comparison. Boundary, occupancy and transaction coverage belongs to task 3.2.

### D4. Extend existing observations and migrate maintained interfaces

Extend `CacheSnapshot`, native setup/statistics marshalling and Python statistics with a separate `retention_declines` tuple of publicly typed immutable `(kind, reason, count)` records. The vocabulary and pair-fallback recording rules belong to the delta. Keep these counters outside `BypassReason`; existing bypass and oversized observations and OpenTelemetry instruments retain their meanings. Snapshot inspection supplies the new observations; this change adds no new metric instrument. Record only the final validated decision, never intermediate retries. The unused alternative representation and capacity reclamation of old records are not declined candidates. No new BSON-capacity decline reason is needed: each chosen representation contains one payload, and its maximum-entry rejection remains the existing oversized observation. Preserve cumulative observations after close while clearing live counts.

Add an internal `DECLINED_RETENTION` outcome when neither useful representation can be admitted due to the new policy; snapshots provide its detail. Count-enabled composite success requires the complete pair or namespace fallback, rather than a successful independent identity `put`. Facades must deliver the native result for either outcome. Keeping the existing bypass vocabulary avoids treating a successfully cached read as bypassed. Redefining bypass metrics would be a wider compatibility change, and adding dedicated OpenTelemetry instruments is not necessary to observe the safeguard. No additional research is needed for this separation; task 3.1 verifies that existing series remain unchanged.

The separate naming decision is a direct pre-1.0 rename because `SharedCacheConfig` already uses the selected name and the current local name suggests cross-process sharing. Compatibility aliases add ambiguous constructor precedence and a second snapshot name without a demonstrated consumer need. Keeping the name avoids migration but preserves that ambiguity. No additional compatibility investigation is required: the selected policy deliberately requires consumer source updates, without claiming there are no external consumers.

Update `shared.py`, coordinator core construction and its group-observation `cache` mapping, along with readers and tests of that mapping; all cooperating processes use one installed version. This is a same-version observation-field update, not a shared request/response protocol redesign. Preserve versioned reports and archived OpenSpec artifacts. Update maintained executable research/benchmark code that still constructs current configuration. Historical instructions tied to old versions retain their original identifiers. Migration guidance belongs to release notes, while current API guidance uses only current names.

### D5. Qualify using a focused extension of the existing harness

Extend `research/process_memory/measure.py`, retaining its fresh-process checkpoints and separate MongoDB process. It currently has scenario selection and repetitions, but no limit parameters, smaller workload selection, per-phase timing or admission-latency distribution. Add only those controls/measurements needed below. Keep workload definitions and the collector common to frozen `main` and candidate builds, adapting the configuration keyword at build registration rather than timing exception-based fallback. Record exact commits, Python, MongoDB image, wheel identity, workload sizes and limits.

First run a bounded disposable-server preflight in both APIs to verify expected admissions, a subsequent retained-key hit, a rejected long key, alias capacity and clean teardown. Select a key threshold strictly between the measured one-field and long-filter charges and freeze it before candidate timing. Begin with 4,096 retained keys and 8,192 distinct reads; choose final sample counts from baseline-only duration so one acquisition with all repetitions finishes within 30 minutes. If these sizes cannot expose a stable memory difference, record that limitation and preregister a larger focused cell instead of claiming a saving from noise.

Include one- and two-slot empty-cache controls plus a larger cache prefilled at half and full occupancy with unrelated values and aliases. Exercise repeated unique-key and `_id` reads, many aliases resolving to one identity, processed writes to unrelated documents in the same collection, and writes to the matched identity. Do not assume an unrelated write causes an origin read on the existing policy: its alias can already preserve identity reuse. Measure actual hit/miss paths, alias resolutions, origin commands, record/payload occupancy, evictions, retention declines, complete-operation CPU and latency. Report policy-driven occupancy differences alongside equal-residency controls rather than calling fewer retained records a cheaper entry. Use the same repetition and acquisition bound as the other D5 cells, reducing baseline-selected sample counts if necessary.

Record cold and warm phase wall time and process CPU, P50/P95/P99 read latency, origin query counts, snapshot deltas, occupancy and existing memory checkpoints through clear/close. Add a focused alias churn/capture case using the existing core ownership tests and memory tools. For one identity, publish and individually remove 256, 1,024 and 4,096 aliases with fixed-size keys, on both native and Python cores with disabled/enabled limits; size the enabled cap to allow each setup. Compare repeated cumulative CPU/allocation cost and retention after cleanup, distinguishing linear membership work from unavoidable key hashing. Repeat bounded publish/remove cycles with captures held and released to demonstrate bounded state and capacity reuse. ## Risks / Trade-offs

- Opaque scalar referents can dominate real memory despite a small shallow charge → document that exclusion and test such a scalar without promising an RSS bound.
- Sizing callbacks and finalizers can reenter the owner → preserve revision checks and deferred destruction, with operation-order coverage.
- Alias reclamation can increase unique-key misses → record origin reads as well as heap savings; never describe a coverage reduction as a faster cache operation.
- Independent native-owner work can move the same seam → reconcile against the checked-out implementation before applying these tasks, keeping the accepted contract.

## Migration Plan

Ship the naming change and optional safeguard in one unreleased change. Release notes provide the configuration/snapshot replacements. Applications that retain defaults receive the existing admission policy after updating the renamed API. Rollback is a package-version rollback with corresponding consumer source changes; there is no stored-data migration. Keep the change active until both approved parts are complete, or record any concrete blocker in issue #337 before considering a split.
